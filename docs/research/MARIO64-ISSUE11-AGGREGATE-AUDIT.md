### Resolved B-button branch from the original checkpoint

The older #36/checkpoint wording that called the B path “unlocated” is stale for the observed `0x00800380` transition. In the exact USA ROM, the 4-byte-aligned caller window `[0x1BA30,0x1BA54)` (mapped PC `0x80260A30..0x80260A54`) has SHA-256 `9507025177ac6a6fc7763a44e69409784ba800e06c4c980a064b9e1214e728d8`. At ROM `0x1BA30` it loads the input halfword at argument `+2`; `andi ...,0x2000` gates the branch; on that branch it passes action word `0x00800380` to the common setter `0x80252CF4`. This static gate is corroborated by two rows in the original batch 04 capture: row 858 records B pressed (`buttonsPressed=0x4000`), Mario-input candidate `0x2020`, prior action `0x0C00023D`, current action `0x00800380`, state 1/timer 6; row 960 repeats the B edge and action from idle `0x0C400201`. The runtime transformation from B's controller mask `0x4000` to derived input bit `0x2000` is consistent with the later #40 input mapping. The numeric action's low ID is `0x380` and its high flags include `0x00800000`; the pinned source header calls this `ACT_PUNCHING`, but target-ROM evidence here establishes the transition and encoded flags, not a complete behavior label or handler body. Other B gates are separately documented in #40 and must not be conflated with this transition.

## Remaining bounded work

The remaining work is bounded to the following evidence limits; none changes the measured behavior claims above:

1. If the integrated implementation needs exact Mario-update counts, measure those updates against the established main-loop counter for the relevant actions. Do not expand this into a VI event-producer audit unless that timing is required.
2. Add only surface branches needed to characterize a currently measured path; water, quicksand, moving platforms, alternate controllers, and broad surface matrices remain explicit limits.

Any further item needs an exact-ROM branch where static claims are made, a documented baseline/input sequence, sanitized scalar trace, and explicit limits. Do not infer meanings from reconstructed-source labels or treat counter-pair equality as an atomic read. No gameplay prototype is authorized by this audit; the project sequence still requires both research dossiers and the #18 agent-led readiness review first.

## Reproduction and handling

Start from the exact ROM, Project64, N-Rage, helper, sampler, and baseline identities recorded in each linked report. Restore the baseline before each trial, start the uniquely named external sampler before sending keys through the guarded helper, and stop/flush through the documented marker. Preserve all original files. Publish only the sanitized numeric traces and reports; never upload the ROM, game assets, raw RAM, or save states.

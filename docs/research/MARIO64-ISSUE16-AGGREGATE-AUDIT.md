## How the systems connect

The source entry clears the no-load region before OS and thread startup. #62's selected native entry identifies the BSS clear range `[0x8033A580,0x80367460)`, length `0x2CEE0`; this is a static instruction finding, not a BSS capture. Source thread 3 creates queues and loads engine code before starting audio and game threads. VI, SP, DP and SI event paths route messages and tasks as described in #61; the relationships do not supply measured event timing.

Source loading paths allocate and DMA raw or compressed data, decode MIO0 where requested, and install a segment base. Segmented addressing translates a segment and offset; it is not a cartridge offset or evidence of machine-code relocation. #58 owns the course-specific inventory and has not observed a controlled load/unload transition. #62's source and native evidence describes generic machinery without establishing every runtime allocation or transfer.

In the graphics path, a CPU-built display list and descriptor pass to the scheduler and SP, with separate SP and DP completion paths. The USA old Fast3D candidate is a unique exact 5,128-byte code match at ROM `[0xE6330,0xE7738)` and a 2,048-byte data match at `0xF4AC0`; the earlier 4,096-byte task-field window is a prefix, not the entire program. #63 maps all five declared overlays and the 208-byte boot match; its static boot analysis distinguishes the `0xF80` load from the `0x0F60` entry. The documented decoder is `spimdisasm` 1.42.4 with Rabbitizer 1.16.2. Actual graphics task descriptor and execution timing remain unobserved.

For audio, source builds synthesis commands and a type-2 SP task, with sample DMA and a later AI buffer submission. #64's pinned JP/US/EU audio program has a unique full 3,616-byte code match at ROM `0xE7740` and 704-byte data match at `0xF52C0`; assembled SH/CN alternatives have no exact full-window match. A source submission does not prove AI acceptance, DMA completion, RSP execution or audible output. #13 and #50 own presentation and sound-request research.

The USA source save structure is 512 bytes with paired file and menu copies and signatures; #65 corroborates selected application and OS code windows but does not infer actual save bytes from the structure. Source wrappers retry reads/writes, and callers can ignore write status. Cached game-over reload is distinct from a fresh EEPROM read, so a changed in-memory copy is not proof of durability. #59 owns objective and progression content and #56 owns life/pickup interaction evidence.

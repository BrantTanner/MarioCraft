# Mario 64 grounded movement on flat ground (issue #38)

**Status: complete for tested normal-floor conditions; see limits below.**

This note measures grounded acceleration, release, braking, steering, and N-Rage input magnitude in the USA retail ROM. It keeps exact ROM evidence distinct from source navigation and from the emulator's runtime observations.

## Scope and provenance

- ROM: `Super Mario 64 (USA).z64`, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`; runtime used a byte-identical analysis copy. The original file was read-only.
- Runtime: Project64 3.0.1.5664-2df3434, executable SHA-256 `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`; N-Rage 3.0.1.5664, DLL SHA-256 `8B06D0BC29DEC6233640400E15051B945923BB6283E290B40AF64016992E6C20`.
- Calibration profile: controller 1, Real N64 Range enabled, PadDeadZone 5. The 100% and 40% N-Rage range settings were checked in the UI and verified in `NRage.ini` after saving.
- Sampler: Project64 `events.ondraw`, bounded to 7,200 records/14,400 callbacks, reading RAM only. Rows carry host `Date.now()` milliseconds and paired reads of global loop counter `0x8032D5D4`. Host draw rows are not emulator frames: each capture produced 7,200 rows over about 120.2 seconds; the counter advanced 3,599 and both counter reads agreed in every row. The counter is useful as a bracket, not proof of one universal physics cadence.
- Inputs were sent by the guarded Project64 helper. It verifies the exact clone executable, PID, HWND, title, and foreground focus; it only sends whitelisted controller keys and releases them in `finally`. Helper call timestamps are recorded in the companion trace; this report uses no PID/HWND or local machine paths.
- The reproducible baseline save is `tools/issue11-local/issue35-mario-gameplay-baseline.pj.zip` (1,387,126 bytes, SHA-256 `6E2C8265A8A9A19761BCC6CE29FA20694FAD5444B325B1F22CA987776A2D6DFE`). Each named trial began from this saved courtyard state (lives 4, stars 0), with starting ground `y=260`, floor type 0 and normal-Y 1.0. A second exploratory hold in the Range-40 long capture was not restored and ran on a slope; it is excluded. Several other held inputs reach the slope; those rows are also excluded from flat-ground measurements.

## Exact ROM evidence

The verified ROM mapping is limited to offsets `0x1000..0xE855F`: `PC = 0x80245000 + ROM offset`. Within that verified range, grounded speed/steering routine `FUN_80265244` maps to ROM offset `0x20244`, and the full 532-byte function body `[0x20244,0x20458)` has SHA-256 `552FC0FE17B3DEB81F6788AFA0214C6334E6051C54ACD768A68D551FBC28758A`. Its direct instructions establish:

- Floor type 9 selects a forward-speed target of 24.0; other or missing floor data selects 32.0. The target is capped by Mario's intended magnitude at `+0x20`.
- If quicksand depth at `+0xC0` exceeds 10, the target is multiplied by `6.25 / depth`; at depth 10 or less it is unchanged. The trial depth was 0.
- On the flat-floor branch (normal-Y at least the runtime threshold `0.949999988079071`), negative speed at `+0x54` gets `+1.1`; nonnegative speed no greater than target gets `1.1 - speed/43`; speed above target gets `-1.0`. The separate hard cap is 48.0. This predicts a bounded stepwise approach, possible overshoot and correction, and a separate cap; it does not make the target an observed sustained maximum.
- Mario's facing yaw at `+0x2E` turns toward intended yaw `+0x24`, with maximum step `0x800` units. With 65536 units per full turn, that is 11.25 degrees. The routine then calls slope/velocity handling at `0x80264B54` (ROM offset `0x1FB54`, verified range).

The acceleration body `[0x20244,0x20458)` and slope/velocity helper `[0x1FB54,0x1FD80)` were extracted from the exact USA ROM and hashed locally. Their SHA-256 hashes are respectively `552FC0FE17B3DEB81F6788AFA0214C6334E6051C54ACD768A68D551FBC28758A` and `8EEEAF8A881C226AA35D843C610A376C59F808F9901BB9021119C577803D199E`. The referenced acceleration constants at runtime RAM `0x80336AC8` and `0x80336ACC` had raw float bits `0x3F8CCCCD` (1.1); threshold RAM `0x80336AD0` was observed as `0.949999988079071`. These data addresses lie outside the verified ROM mapping prefix, so this report does not assign them a ROM offset. The 48.0 cap is a separate instruction immediate in the mapped function. The intended-magnitude field relation is confirmed by runtime observations below; this report does not claim a mapped ROM body hash for its producer.

For independent word-level inspection, use the USA ROM identified above and `python MarioCraft/tools/issue11-local/disasm_range.py 20244 20458` and `python MarioCraft/tools/issue11-local/disasm_range.py 1FB54 1FD80`. Arguments are half-open ROM byte offsets; the decoder prints each big-endian MIPS word. The ROM identity, script behavior, and verified linear mapping are documented in [issue #36](MARIO64-USA-ACTION-DISPATCH-AND-GAMEPLAY-TIMING-ISSUE36.md).

## Runtime findings

- With N-Rage range 100%, cardinal Up reached raw Y 127, processed Y 64 and input magnitude 64; Mario's intended magnitude was 32.0. The grounded speed routine's 32.0 target is therefore applicable at full cardinal input on the tested floor.
- In an awake, isolated 3-second Range-100 Up hold, flat-ground speed reached 31.5959 before the route left flat ground; the later maximum 32.353 was on a sloped floor and is excluded from flat maximum claims. This is consistent with a 32.0 target and stepwise correction; the trace did not establish a long flat steady plateau.
- At N-Rage range 40%, a short cardinal Up event yielded a stable input plateau raw Y 50, processed Y 44, input magnitude 44 and Mario intended magnitude 15.125. A longer post-wake hold repeated that plateau on flat floor: 128 nonzero-input host rows within 160 flat rows; speed peaked at 15.86033 before the courtyard route left the flat section. This measured peak sits above the 15.125 intended target, consistent with the direct acceleration branch's overshoot/correction; it is not reported as the target itself.
- At range 40%, diagonal Up+Left held raw `(-35,35)`, processed `(-29,29)`, and magnitude `41.01219`; Mario intended magnitude was `13.140624`. On eligible flat rows the facing yaw changed by 10,409 signed units (about 57.13 degrees) across the held-turn window, while speed fell from about 14.08 to 4.81. The trace demonstrates the observed diagonal magnitude and turn response, not an assumed 45-degree facing result.
- At range 100%, cardinal Up produced processed Y and input magnitude 64, with intended magnitude 32.0. The isolated Up1200ms then Down1000ms high-speed trial remained on floor type 0, normal-Y 1.0, y=260: speed fell from about 25.43 to zero and the position reversed its Z direction while facing yaw turned. Forward speed did not become negative in this sample. This is braking and turnaround through facing, not evidence of a negative-speed reverse state.
- The N-Rage/profile relation is measured empirically here; no undocumented N-Rage DLL formula is assumed. Earlier deadzone sweep results are in `MARIO64-ISSUE37-ANALOG-DEADZONE-SWEEP.md`.
- In the first isolated range-100 Up trial, after helper key-up the input magnitude decayed through the plugin's release behavior; once processed input reached zero, sampled speed went from 7.679 to 6.679, 5.679, 4.679 and then 3.679 on successive observed loop-counter values before settling to zero. This is one observed release sequence, not a universal friction constant or per-frame cadence claim. Host draw observations and counter bracketing do not establish a universal Mario physics step.

The measurements cover normal floor, ordinary range-40 input, full range-100 input, release/coast, diagonal input, and high-speed braking/turnaround. They do not measure quicksand response or establish a universal physics cadence. The range-40 input was not replayed against an exact counter-identical seed; its lower peak and the full-range trials are separate restored-seed runs. Do not extrapolate these results to other surfaces, squish states, or controller plugins.

## Trial protocol

All traces used the saved state identified above and began with F7 restore. For the full-range 3-second acceleration, the helper sent a 30ms Up wake pulse, waited 2 seconds, then held Up for 3,000ms. The range-100 braking trial used the same wake sequence, then Up1200ms, a 200ms gap, and Down1000ms. The range-40 turnaround trial used wake30ms, 2 seconds, Up750ms, a 200ms gap, and Down1200ms. The diagonal trial used wake30ms, 2 seconds, Up750ms, a 200ms gap, then Up+Left750ms. The short range-40 cardinal trial used one Up750ms after F7; the longer range-40 hold used Up3000ms, but its 34-second gap after the wake pulse allowed sleep to recur, so early input rows may include waking. The exploratory range-100 release capture used three separate Up750ms events followed by Down750ms and Left750ms; only its first Up release segment is retained in the compact trace. The JSONL input-event records include requested and actual helper durations and relative down/up times.

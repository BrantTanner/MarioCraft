# Mario 64 jump arcs, air control, and advanced combinations (issue #39)

This report documents representative evidence for ordinary jump, airborne steering, backflip, long jump, double/triple jump, sideflip, and the two wall-kick timing paths verified under #41. These are representative Project64 trials, not a statistical timing sweep or matched comparison of every jump arc.

## Identity and method

- Target: Super Mario 64 USA retail ROM, 8 MiB, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. The original file was read only; runtime used the byte-identical local analysis copy.
- Static inspection used the exact-ROM Ghidra project copy and the verified address prefix `PC = 0x80245000 + ROM offset`, valid only for ROM offsets `0x1000..0xE855F`. The source checkout at `n64decomp/sm64` commit `9921382a68bb0c865e5e45eb594d9c64db59b1af` is navigation evidence for names and struct semantics; all PC/ROM intervals below were checked against the retail ROM.
- Runtime: Project64 3.0.1.5664-2df3434, executable SHA-256 `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`; the loaded N-Rage DLL SHA-256 was `8B06D0BC29DEC6233640400E15051B945923BB6283E290B40AF64016992E6C20`. Controller 1 used Real N64 Range on, range 100%, deadzone 5.
- Capture source: the original #39 jump trials used Project64 `events.ondraw`, bounded to 7,200 rows / 14,400 callbacks. Each row reads Mario action/state, position, velocity, controller fields, and the global counter twice; mismatched counter pairs are retained and identified. Host draw callbacks are not treated as game frames. The counter (`0x8032D5D4`) advanced 3,599 during a 7,200-row capture in that setup; counter units are used as bounded timing only. Embedded callback capture faulted during #41 wall-kick work, so those runs used the published [read-only RDRAM locator](mario64-issue41-find-rdram-base.ps1), [external samplers](mario64-issue41-external-capture-38.ps1), and [bounded early/late drivers](mario64-issue41-early-wall-kick-39.ps1).
- Input helper: `issue39-project64-input.ps1` is derived from the reviewed issue #38 helper and retains its exact-process/PID/HWND/title/foreground checks, key whitelist, 3,000ms hold bound, and `finally` key-up behavior. The active N-Rage keyboard config binds logical Z to Space (scan `0x39`), so this issue-specific helper maps `Z` to scan `0x39`; the issue #38 helper's physical letter-Z scan `0x2C` is not a Z-button mapping in this profile. A/B mappings remain X/scan `0x2D` and C/scan `0x2E`. Runtime samples verified all three button masks before interpreting advanced inputs.
- The reproducible courtyard baseline for the original #39 jump trials is `tools/issue11-local/issue35-mario-gameplay-baseline.pj.zip` (1,387,126 bytes, SHA-256 `6E2C8265A8A9A19761BCC6CE29FA20694FAD5444B325B1F22CA987776A2D6DFE`): lives 4, stars 0, starting position `(-1328,260,4354)`, floor type 0, normal-Y 1.0. Those trials restore it with F7 before sampling. The #41 wall-kick trials instead restore the human-input-created runway seed at X=169.68, Y=803, Z=−2679.37, with provenance and hash in the linked wall-kick dossier.

The airborne transition setup initializes normal jump to vertical speed `42 + 0.25*forwardVel`, then multiplies forward speed by 0.8; double jump is `52 + 0.25*forwardVel` and also scales forward speed by 0.8; backflip uses vertical speed 62 and forward speed −16; sideflip uses vertical speed 62, forward speed 8, and sets facing from intended yaw; triple jump uses vertical speed 69 and scales forward speed by 0.8; long jump starts at vertical speed 30, marks the slow animation/state when forward speed is at most 16, multiplies forward speed by 1.5, and caps it at 48. These are transition setup values, not measured peak height or proof of a trigger by themselves. The long-jump function above is its grounded crouch-slide trigger, not the airborne trajectory handler.

The grounded crouch-slide handler tests A_PRESSED and `forwardVel > 10` while the action timer is at most 29 to select long jump `0x03000888`; otherwise it takes another grounded exit. The crouch/stop-crouch handlers branch A_PRESSED to backflip `0x01000883`; the turn-around handlers branch A_PRESSED to sideflip `0x01000887`. The exact-ROM landing selector maps previous actions `0x04000470` (jump land), `0x04000471` (freefall land), or `0x0C000233` (side-flip land-stop) to double jump `0x03000881` when the repeat-jump timer is nonzero and squish is absent. Previous action `0x04000472` (double-jump land) selects flying triple jump with wing cap, triple jump `0x01000882` when forward speed exceeds 20, and ordinary jump otherwise. These numeric action IDs were checked in the exact USA ROM range/hash in the table above; source names are navigation aids. Wall-kick timing is now corroborated by two runtime representatives in [the #41 wall-kick report](MARIO64-ISSUE41-WALL-KICKS.md): an early A edge produces `0x000008A7 -> 0x03000886`, while a late edge produces `0x000008A7 -> 0x010208B6 -> 0x03000886`. Exact gate, dispatcher, setter, and transition-setup evidence is documented there and in the compact traces linked below.

The gravity routine's quarter-height predicate requires Mario flag bit `0x100`, excludes action flags `0x1000` (intangible) and `0x20000` (invulnerable), requires A_DOWN `0x80` to be clear and vertical velocity above 20, and requires action flag `0x02000000` (control jump height). When true, it divides vertical velocity by four. The ordinary branch subtracts 4 and floors at −75; action-specific gravity branches have separate rates. These names/masks follow the pinned source navigation and were checked against the exact-ROM function range/hash above. The sampled Mario vertical velocity is at `+0x4C`; forward speed is at `+0x54`.

## Runtime observations captured so far

The repeated 160 ms normal-jump hold was captured from the F7 courtyard baseline and measured takeoff at Y=302 with vertical speed +38, then release reduced +22 to +5.5 under the quarter-height branch. A separate 750 ms A hold trial appeared to reach a higher peak, but F7 was loaded while the sampler callback was live; the counter reset marks a restore boundary and the run is not a valid controlled hold-duration comparison. No claim that hold duration caused the peak difference is made. Trial 1's older sampler read the action-state/timer pair as a 32-bit combined word at Mario+0x18; the compact sample derives the state from the upper 16 bits and records the separately sampled timer. Later captures use the corrected 16-bit action-state read at +0x18.

- One ordinary jump from the baseline used an A hold around 160ms. The branch selected action `0x03000880`; at sampled takeoff, y moved from 260 to 302 and vertical velocity was 38. While A remained down, sampled vertical velocities went 38, 34, 30, 26, 22; after release, 22 changed to 5.5, matching the exact quarter-height branch. The observed apex was y=459, then the player landed at y=260. This is one observation, not yet a repeatability claim.
- One separate normal-jump trial applied right input after the sampled apex while action `0x03000880` was still airborne. The sampler saw the controller's processed X field rise 0→12→64; Mario's X-velocity field changed from 0 to +10 as X moved from −1328 to −1317.65. The input helper timestamps overlap the airborne samples. This supports in-air steering on this run; it does not establish an axis-independent formula or a universal frame cadence.
- A first attempted long-jump sequence pressed Z before establishing speed; it did not enter the required crouch-slide action. A second sequence built speed before Z but used the wrong physical Z scan code; it also produced an ordinary jump and is excluded as a valid long-jump test.
- Button masks were verified on the corrected helper/profile: logical Z/Space is `0x2000`, A/X is `0x8000`, and B/C is `0x4000` in the sampler's controller record. The trial used for that verification pressed B before Z/A, so it is not used to infer a backflip.
- Trial 8b selected backflip `0x01000883`, then ground pound `0x008008A9`: the helper released all keys after its Z hold, then created a fresh Z-down edge together with A, so this is not evidence that a continuously held Z caused the transition. Its absolute sampled Y peak was 370 and is excluded as a clean backflip arc. Full local trace SHA-256 `301D0559C4E4163C9371DF26D923A3C964BB240A1B8F0999D1D0F1B33FC1530F`.
- A clean, baseline-restored backflip run used Z for 250 ms, followed by A alone for 750 ms. It selected `0x01000883` at counter 4739 (host 03:55:28.933Z); sampled takeoff was Y=322, vertical velocity +58, and forward speed −15.65. The highest sampled Y was 772 at counter 4754. It entered backflip-land action `0x0400047A` at counter 4770 and backflip-land-stop `0x0800022F` at 4774, without a ground-pound action. Helper events were Z 03:55:28.603–28.863Z and A 03:55:28.888–29.648Z. Full trace `issue39-jump-trial-8d-backflip.jsonl`, SHA-256 `675AC15C973CF12A580E6FE8B34AC5F04BF1C2772F4E6D77AAAF47B46251D309`.
- A baseline-restored long-jump sequence built forward speed with AnalogUp for 400 ms, pressed Z+AnalogUp for 80 ms, then A+AnalogUp for 160 ms. Z selected crouch-slide `0x04808459` at counter 4750 with action timer 2 and forward speed 12.3718 on flat floor type 0 / normal-Y 1.0. A selected long jump `0x03000888` at counter 4753; sampled takeoff was Y=290, vertical speed +28, forward speed 17.5476. The sampled apex was Y=500 at counter 4767; long-jump-land `0x00000479` began at counter 4783 and land-stop `0x0800023B` at 4789. Helper events were AnalogUp 03:59:47.788–48.204Z, Z+AnalogUp 48.226–48.315Z, and A+AnalogUp 48.338–48.503Z. Full trace `issue39-jump-trial-9b-longjump.jsonl`, SHA-256 `117B1409052FD44BF423A77BF7A7729EFFB10BAD26495A098176F28015329973`. A separate earlier long-up attempt was stopped prematurely based on a late terrain snapshot; it is excluded and does not support a gameplay conclusion.
- A double-jump sequence restored the same F7 save, built speed with AnalogUp for 600 ms, then used A+Up, Up, A+Up, Up, A+Up. The first A selected normal jump `0x03000880` at counter 4833; after landing, the second A arrived at counter 4855 while the repeat-jump timer was still nonzero and selected double jump `0x03000881`. That jump reached Y=574.35 at c4863 and entered double-jump-land `0x04000472` at c4874. The third A arrived at c4883, after the timer had reached zero; it selected a normal jump, not a triple jump. ## Wall-kick runtime evidence

The wall-kick gap identified in the earlier checkpoint is now covered by [issue #41's exact-ROM and runtime dossier](MARIO64-ISSUE41-WALL-KICKS.md), its [sanitized scalar trace and input-edge samples](MARIO64-ISSUE41-WALL-KICK-TRACE-SAMPLES.json), and its [evidence manifest](MARIO64-ISSUE41-WALL-KICK-EVIDENCE-MANIFEST.json). The same selected rows and edge events are appended to this report's [combined jump trace JSONL](MARIO64-ISSUE39-JUMP-TRACE-SAMPLES.jsonl), tagged `wallkick-early` and `wallkick-late`.

- **Early wall kick (trial 39):** from the runway seed, A was sent predictively just before the expected wall contact. At seq 1011/counter 53696, Mario hit a vertical wall with normal +X in `0x000008A7`; at seq 1012/counter 53697, the A-pressed mask was `0x8000`, action became `0x03000886`, and previous action was `0x000008A7`. The first selected kick row had Y=1080.9573 and vY=+58. A later sample reached Y=1311.4573 at counter 53704 and entered jump-land `0x04000470` at counter 53721. This demonstrates the early branch; it does not measure a universal input-delay window.
- **Late wall kick (trial 38):** after the same wall-hit action, Mario entered soft bonk `0x010208B6` with wall-kick timer 5. A keydown occurred between sampled timer values 3 and 2; the next accepted kick row showed `0x03000886`, previous action `0x010208B6`, Y=1053.5015, and vY=+58. Its sampled apex was Y=1284.0015 at counter 53856; jump-land `0x04000470` began at counter 53872.
- **Contact-only control:** trial 36 reached wall-hit `0x000008A7` and soft bonk `0x010208B6` without another A edge, corroborating the contact path that precedes the late timing branch.

The common action setter's transition setup sets wall-kick action `0x03000886` to vY=62 and minimum forward speed 24, clearing the wall-kick timer; the sampled first post-transition rows show vY=+58 after runtime update. The early handler's earlier vY=52 write is superseded by that shared setup. The exact ROM intervals and SHA-256 values, including the corrected late gate range `[0x2833C,0x283C4)`, are in the #41 dossier. Its ROM mapping is valid only for offsets `0x1000..0xE855F`.

The two trajectories have different takeoffs and input timing, so their peak heights are not a controlled comparison. Together with the other jump representatives, they complete the documented representative action coverage; they do not constitute an exhaustive timing sweep or prove frame-perfect timing for all setups.

## Evidence coverage and limits

The #39 evidence package now has representative runtime coverage for normal jump, air steering, clean backflip, long jump, double/triple jump, sideflip, and early/late wall kicks. Trigger, selector, gravity, and setup conditions are tied to exact-USA-ROM ranges and hashes. The contact seed and both wall-kick paths were completed under [#41](https://github.com/BrantTanner/MarioCraft/issues/41). The evidence does not claim a statistical timing sweep or a controlled comparison of all arc heights. Full local captures remain ignored. The standalone sampler is [issue39-project64-sampler.js](issue39-project64-sampler.js), and the foreground-checked input helper is [issue39-project64-input.ps1](issue39-project64-input.ps1). The published sample JSONL now has 171 populated records and includes per-trial baseline/full-trace hashes, helper key-down/key-up event metadata, counter/time provenance, action transitions, positions, velocities, wall/floor details, and button state. Logical Z was sent through N-Rage's Space binding (scan `0x39`, controller mask `0x2000`); repeat that profile-specific mapping when using the helper for issues #40/#41.

For standalone ROM verification, use the standard-library decoder/range-hash script and invocation documented in [issue #36's ROM listing section](MARIO64-USA-ACTION-DISPATCH-AND-GAMEPLAY-TIMING-ISSUE36.md#standalone-rom-listing-and-range-hash-script). For example, run the listed script against the immutable USA ROM with ranges `0xDE5C:0xE0A0`, `0x1CDB4:0x1CF70`, `0x21AF8:0x21D4C`, `0x23168:0x23338`, `0x11584:0x1160C`, `0x1161C:0x119F8`, `0x2833C:0x283C4`, `0x28988:0x28B54`, and `0x2AB04:0x2B104`; it checks the ROM SHA and emits the range hashes used above.

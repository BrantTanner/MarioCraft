# Mario 64 USA collision queries, geometry, and boundaries (#42)

This dossier traces the USA rev0 collision-query consumers and records representative Project64 behavior for floor/slope, wall, ceiling-query, and ledge cases. It keeps object hitbox fields separate from the radii and heights passed to geometry queries. The local raw process captures and state archives remain local; only selected scalar samples are published.

## Identity and evidence method

- ROM: USA rev0, 8 MiB, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. The original ROM was preserved read-only; runtime used its byte-identical analysis copy.
- Emulator: Project64 3.0.1.5664-2df3434, executable SHA-256 `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`; N-Rage Real N64 Range, stick range 100, deadzone 5.
- The read-only external sampler validates process/window identity and ROM hash and reads Mario, controller, floor, wall, ceiling, and Mario-object fields. Each row brackets those reads with guest loop-counter reads. Equality is a consistency check, not proof of an atomic snapshot. Rows with unequal brackets remain distinguishable in the sanitized trace.
- Scalar coordinates use the game’s world-space units. The pinned decompilation navigation snapshot comments that a level grid spans 16,384 X/Z units (`−8192..8192`) and collision cells are 1,024 units. These particular grid bounds are source-navigation evidence, not independently derived from an exact-ROM routine here; no real-world length conversion is claimed.

## Query callers and consequences

The USA rev0 Ghidra export in `tools/issue11-local/issue42-candidate-fns.txt` was mapped against the exact ROM. These anonymous functions were identified from their operands, called routines, loop structure, and result branches; the hex PC-to-file mapping is PC minus `0x80245000` and is valid in the checked ROM span. The bounding ROM slices (end-exclusive) are:

| PC / role | ROM bytes | SHA-256 |
| --- | --- | --- |
| `0x80255B04` ground quarter-step query/classification | `[0x10B04,0x10D88)` (644) | `256D52F30FFDB533C68E2D82F3C2C0A57FA7DC811FE6FED2DBD002661AADFFB2` |
| `0x80255D88` four-quarter ground-step caller | `[0x10D88,0x10EC4)` (316) | `F40BEE52CE29F850029DEE2828FC89402B75877D7C7336DEA90955E0398A21EC` |
| `0x80255EC4` ledge-grab candidate/result checks | `[0x10EC4,0x110AC)` (488) | `7CFF1DFB0E2D00CA40A547B9376D42F349E0D1A140798B9642AC53B3754EF6E2` |
| `0x802560AC` air quarter-step query/classification | `[0x110AC,0x114E0)` (1076) | `FD272B7C245D6F2DA296C503F9E350B19544FD8181D479C102BEC609035647B8` |

The Ghidra function-body ranges (including split tail blocks) are respectively `80255B04..80255D6B` + `80255D74..80255D87`, `80255D88..80255EAB` + `80255EB4..80255EC3`, `80255EC4..80256093` + `8025609C..802560AB`, and `802560AC..802564C3` + `802564CC..802564DF`. Hashes above cover each contiguous bounding slice, including any gaps. The verified immediate constants in the ground-quarter routine are 30/24 and 60/50 wall query offset/radius pairs, 100 units floor-height tolerance and 160 units floor/ceiling clearance; the function also queries floor and ceiling and classifies wall angle into stop/continue outcomes. The caller computes one-quarter velocity displacement and repeats at most four times. It breaks on numeric result 0 (left ground) or 2 (stop); the source enum labels 1 as no change and 3 as wall/continue. These labels are cross-checked against the source navigation enum while the numeric branches come from the exact-ROM caller. The air-quarter routine uses wall offsets 150 and 30 with radius 50, queries floor and ceiling, and branches to landed, wall, or hangable-ceiling outcomes. The ledge-grab candidate checks non-rising Y velocity and displacement against wall normal/velocity, offsets the floor search 60 units behind the wall and starts it at Y+160, then rejects a candidate whose floor is no more than 100 units above the proposed position. These are ROM-derived query/branch facts; they do not establish a universal step height.

The linked `source-navigation-9921382` files are source-navigation aids used to check names and enum meanings, not proof of ROM bytes. In particular, `0x80255B04` is the quarter-step routine, not the per-frame geometry-input updater. The exact ROM operands and its callers are the basis for the role labels and ranges above.
A wall query is demonstrated directly in runtime. From the verified lower-platform seed (E3AF hash below), short forward input reached center Z `−3054.0` against the `+Z` face at Z `−3104`; the retained position was exactly 50 units from the face. The sampled wall normal was `(0,0,+1)` and the floor remained at Y `803`. That agrees with the large 50-unit wall-probe radius. The object’s independently sampled candidate hitbox radius was 37, so its value is not the wall-query radius. A smaller 24-unit wall test is present in the exact caller but was not separately isolated in runtime; the observed stop distance supports the 50-unit probe only.

The floor query is evidenced by ordinary floor and sloped-floor rows. The courtyard slope sample reports floor Y `322.4548` with normal-Y `0.97015643`, while Mario’s Y matches that queried floor. On the lower platform, floor type 0 reports Y `803` and normal-Y `1`. These rows support a usable surface-height query and slope normal, not a universal floor classification threshold. The ceiling query at the lower-platform seed repeatedly returned Y `1537.0001`, type 0, normal-Y `−0.7071068`; it remained a queried overhead surface through a stationary jump peaking at Y `957.5`. This is a query result, not a ceiling contact. The geometry’s measured clearance was `1537−803=734` at the resting floor and `1537−957.5=579.5` at that sampled jump height; both exceed 160. A hangable ceiling contact was not tested.

The Mario-object fields observed at baseline are hitbox radius candidate 37, height candidate 160, and down-offset candidate 0; field offsets/types remain candidates pending cross-check against the exact-ROM runtime object initializer. The separate hurtbox slots were read but are not used to infer the movement collision body. The 160 value is corroborated as a gameplay clearance constant in exact query callers, but this alone does not prove that the object hitbox height field drives floor/wall/ceiling collision. Do not substitute hitbox 37/160 for query radii 24/50 or vertical probe offsets 30/60/150.

## Step, ramp, and ledge evidence

The lower platform contains a sloped ramp; it is not a discrete step test. The sanitized captures show continuous floor-height and normal changes on the courtyard slope and a floor-to-air transition on the narrow outer edge. The all-upward-triangle floor profiler uses barycentric X/Z interpolation (`normalY > 0`) to avoid missing ramps. Candidate regions were rejected when a nearby vertical wall or castle door route confounded a walk-off: at the south face near Z `−3104`, Mario stopped at the wall; a later route triggered `ACT_PUSHING_DOOR` (`0x00001321`), then door-warp/dialog actions, so it is excluded as ledge evidence.

The primary controlled walk-off is the #42 external capture `issue42-ledge-approach-z-03.jsonl` (83 sampled rows; local SHA-256 is in the manifest). The run started on the lower-platform route at `(−497.9889,803,−2605.8289)` and moved toward the rising ground-approach ramp. Seq 55 / counter 52486 was still grounded at `(−451.3446,957.6312,−1959.9868)`, floor 957.6312, normal-Y 0.9999929. Seq 56 / counter 52487 changed to `ACT_FREEFALL` (`0x0100088C`) at `(−449.6514,957.6951,−1936.5425)`; the floor query returned 834.98865 with normal-Y 0.98626363 and there was no wall pointer. The queried floor was 122.70645 units below Mario, beyond the exact routine's `floorHeight + 100` acceptance boundary; adjacent static floor interpolation gives 957.627532 at seq55 and 834.897760 at seq56, matching the runtime queries within 0.1 units. Input magnitude was 64, processed-Y −64, and no A/B button was down or pressed. The trace then fell through seq 62 (Y 873.6951, vY −28) and landed at seq 63 / counter 52496 in `0x04000471` at Y 869.1545; seq 64 held the landing state with vY 0 at Y 874.3463, then seq 67 resumed ground movement. Thus the observed fall was real and followed by a landing, rather than an inference from a missing static triangle. The guarded input log records a preparatory AnalogDown hold requested for 650 ms (scan code `0x50`, edge key-down 09:47:01.4170394Z to key-up 09:47:02.0833566Z), then the captured AnalogDown hold requested for 1,800 ms (scan code `0x50`, edge key-down 09:47:28.1357304Z to key-up 09:47:29.9497884Z). The sampler began at 09:47:27.371Z; sampled seq 56 entered freefall at 09:47:29.508Z, before key-up, and seq 63 landed at 09:47:29.787Z. The processed stick was −64 on Y during the route, with no A/B press. The selected key edges are included in the sanitized sample file; the full helper log remains local.

A second walk-off observation is reused from issue #41 trial A-29. It begins at `(−487.7145,958.4541,−1740.0052)`, takes a short wake pulse, then runs with AnalogDown+AnalogLeft. Verified key-up events occurred at seq 1499, where Mario was at `(−546.7951,957.8830,−1892.9364)`, still in ground-movement action `0x04000440`, with no wall pointer. At seq 1500 he was at `(−555.3874,957.8379,−1908.3236)` and entered `ACT_FREEFALL` (`0x0100088C`); no A or jump button was pressed. Later equal-bracket rows show falling Y `693.8379` and `−176.1621`, with no floor landing in that retained window. The original driver validates an F7 starting coordinate/action corridor, not an archived file hash; a matching run-up archive exists, but exact archive-to-F7 binding was not established. Treat A-29 as supplemental controlled walk-off evidence with a seed-binding limit, not an exact replay recipe.
The code-derived ledge-grab path is narrower than “fall near a wall”: it requires non-rising vertical velocity and displacement by a wall collision against the velocity, then searches for a floor 60 units behind the wall from `nextPos.y + 160`; it rejects the candidate if the found floor is no more than 100 units above `nextPos.y`. The A-29 walk-off had no wall pointer and therefore does not demonstrate a ledge grab. No successful ledge-grab or isolated controlled step-up threshold trial was captured. Step-up thresholds therefore remain code-derived; runtime verifies a ramp, wall stop, and walk-off/landing consequence, not every discrete step boundary or special-surface case.

## Reproduction and limits

The lower-platform source save is `tools/issue11-local/seeds/issue41-lower-platform-y803-z2670.pj.zip`, 1,434,741 bytes, SHA-256 `E3AF591D10EE312438A88F57351ADA6CB35D1B0A8BE80128B38D7242429DE616`. Use Project64 System → Load… (Ctrl+L) to select this archive, then numerically verify the loaded coordinates and floor fields before sampling. The short wall recipe uses the guarded input helper for AnalogUp in 100–150 ms pulses with telemetry checks until Z is about −3054; stop there, flush the capture, and do not continue toward the castle door. For the floor-to-freefall route, restore that same lower-platform archive and use the external sampler while steering in 100–150 ms analog pulses toward the ground-approach ramp. Use camera-yaw-relative direction selection to approach `(−452,958,−1960)`; once the floor height begins to depart from Mario Y, keep pulses short and capture through the `0x0100088C` transition and subsequent landing. Bound the approach to 30 pulses and stop if coordinates leave the castle-grounds route. For the captured recipe, the verified lower-platform archive was the route origin; the sampler opened after the preparatory movement at `(−497.9889,803,−2605.8289)`. The guarded helper log supplies both AnalogDown edge pairs and hold durations. The pre-capture route was 650 ms AnalogDown from the archive; the captured route held AnalogDown for 1,800 ms while the sampler ran. Use the fresh sample coordinates, camera yaw, action, and floor height to verify the start and reproduce the route; emulator input-to-game-frame timing is still not guaranteed identical.

After loading the archive and preparing the start point with AnalogDown for 650 ms, verify the current coordinates and locate the process-specific RDRAM base. The locator is [mario64-issue41-find-rdram-base.ps1](mario64-issue41-find-rdram-base.ps1); it verifies the ROM-prefix mapping and returns candidates whose fields must match the prepared state. The issue #42 sampler is [mario64-issue42-external-capture.ps1](mario64-issue42-external-capture.ps1). From `docs/research`, with Project64 foreground:

```powershell
$projectRoot = (Resolve-Path '..\..').Path
$exe = Join-Path $projectRoot 'tools\issue11-local\pj64-portable\Project64.exe'
$rom = 'C:\Users\brant\Documents\MarioUSA-local-analysis-copy.z64'
$target = Get-Process -Name Project64 | Where-Object { $_.Path -eq $exe } | Select-Object -First 1
$targetPid = $target.Id
$targetHwnd = [long]$target.MainWindowHandle
& .\mario64-issue40-project64-input.ps1 -ExpectedPid $targetPid -ExpectedHwnd $targetHwnd -TargetInstance Issue11Portable -Key AnalogDown -HoldMs 650
Start-Sleep -Milliseconds 800
$scan = & .\mario64-issue41-find-rdram-base.ps1 -TargetPid $targetPid -Project64Path $exe -AnalysisRomPath $rom | ConvertFrom-Json
$match = @($scan.candidates | Where-Object { $_.fieldsValid -and [math]::Abs($_.x + 497.9889) -lt 3 -and [math]::Abs($_.y - 803) -lt 3 -and [math]::Abs($_.z + 2605.8289) -lt 5 })
if ($match.Count -ne 1) { throw 'No unique valid candidate matches the prepared route start.' }
$base = $match[0].hostBase
$trial = 'issue42-ledge-replay-01' # choose a new unique ID each run
$traceDir = Join-Path $projectRoot 'tools\issue11-local\pj64-portable'
$stale = @('.jsonl','.progress.jsonl','.stop') | ForEach-Object { Join-Path $traceDir ($trial + $_) } | Where-Object { Test-Path -LiteralPath $_ }
if ($stale) { throw 'Trial ID already exists; choose a fresh unique ID.' }
$sampler = Join-Path (Get-Location) 'mario64-issue42-external-capture.ps1'
$capArgs = '-NoProfile -File "{0}" -TrialId {1} -TargetPid {2} -TargetHwnd {3} -HostBaseHex {4} -ProjectRoot "{5}" -AnalysisRomPath "{6}" -Limit 420 -PollMs 15' -f $sampler,$trial,$targetPid,$targetHwnd,$base,$projectRoot,$rom
$samplerProcess = Start-Process -WindowStyle Hidden -PassThru -FilePath (Join-Path $PSHOME 'pwsh.exe') -ArgumentList $capArgs
$progress = Join-Path $traceDir ($trial + '.progress.jsonl')
$deadline = [datetime]::UtcNow.AddSeconds(10)
while (-not (Test-Path -LiteralPath $progress) -and [datetime]::UtcNow -lt $deadline) { Start-Sleep -Milliseconds 50 }
if (-not (Test-Path -LiteralPath $progress)) { throw 'Fresh sampler progress did not appear.' }
& .\mario64-issue40-project64-input.ps1 -ExpectedPid $targetPid -ExpectedHwnd $targetHwnd -TargetInstance Issue11Portable -Key AnalogDown -HoldMs 1800
New-Item -ItemType File -Path (Join-Path $traceDir ($trial + '.stop')) | Out-Null
# Stop and wait for the sampler to flush before any state reload.
$null = $samplerProcess.WaitForExit(10000)
$jsonl = Join-Path $traceDir ($trial + '.jsonl')
if (-not $samplerProcess.HasExited -or -not (Test-Path -LiteralPath $jsonl)) { throw 'Sampler did not exit and flush the unique JSONL within 10 seconds.' }
```

The actual capture used a 650 ms AnalogDown preparation hold, then a 1,800 ms AnalogDown hold during the fresh sampler; use the same short bounded pulses only after verifying the expected restored scene. The helper releases keys in `finally`. Create a unique `$trial` for each run and use the matching `.stop` marker shown above; wait for the `.jsonl` flush before any state reload. Never interpret a title/attract scene or a stalled counter as a valid measurement.

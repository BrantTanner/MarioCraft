# Mario 64 special-surface inventory (#43)

This dossier records a finite candidate inventory of 147 source-listed surface IDs for USA rev0, exact-ROM consumers verified so far, and runtime evidence that remains available. Coverage is intentionally stated per consumer: the source-navigation enum supplies candidate names and IDs, while the ROM ranges below establish only the listed target branches. Every ID is assigned a candidate family and an MVP-scope note in the inventory; source-only classifications do not claim that a target consumer was found.

## Identity and evidence rules

- Analysis ROM: Super Mario 64 USA rev0, 8 MiB, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. The original ROM was preserved; Project64 loaded the byte-identical local analysis copy.
- Emulator: Project64 3.0.1.5664-2df3434, executable SHA-256 `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`, N-Rage, Real N64 Range, stick range 100, deadzone 5.
- Surface inventory: [`mario64-issue43-surface-inventory.csv`](mario64-issue43-surface-inventory.csv) lists all 147 source-listed IDs and separates decimal from hexadecimal. It currently marks 26 IDs with verified exact-ROM consumers scoped in `targetBehavior`, 101 as source-only candidates with exact-ROM use unresolved, 19 as source-commented “unused” without proving ROM absence, and one (decimal 41 / `0x29`) with a reused runtime observation but no verified consumer in the scanned ROM families. Rows also classify all 147 candidate families and note whether each is an MVP-relevant candidate or a course-specific/undecided mapping. A source label or `unused` comment never establishes target-ROM use or absence.
- Source-navigation snapshot: commit `9921382a68bb0c865e5e45eb594d9c64db59b1af`. Its names/comments are candidate labels, not proof of target-ROM use. In particular, numeric values must not be conflated: surface type decimal 19 is hex `0x13`; floor class `0x13` is a separate mapped field.
- PC-to-ROM conversion for the pinned USA rev0 image is `ROM offset = PC - 0x80245000` in the mapped range. The query notes below give exact bounding slices and SHA-256 digests. Endpoints are exclusive.
- Runtime sampling uses external `ReadProcessMemory` with query/read rights only. The issue #43 copy of the sampler is [`mario64-issue43-external-capture.ps1`](mario64-issue43-external-capture.ps1); it records signed `waterLevelS16` from MarioState+`0x76` using the verified big-endian guest halfword `XOR 2` decode. The separately named issue #42 sampler was restored to its published logic and remains without this #43 field.

## Runtime observations and recipe

Prior #42 captures are reused only where their fields are directly relevant: floor type 0 / normalY 1 on ordinary ground, floor type decimal 41 (`0x29`) on the observed courtyard slope, and ceiling query type decimal 5 (`0x05`) without contact. None of these is a measured slippery-surface friction coefficient or a surface-contact action change.

The #43 sampler's `waterLevelS16` field was observed in a water-box footprint while Mario stood on ordinary dry floor: at `(-503, 803, -2670.075)`, floor type 0, floorY 803, water level -81, action `0x0C000203`. The water surface is therefore not itself Mario's floor type in this observation. The lower-platform numeric trace is `tools/issue11-local/pj64-portable/issue43-waterbox-lower-seed-01.jsonl`; its metadata is adjacent. This proves the field value/read and its separation from floor type, not swimming.

The bounded route did not reach the target water box. The useful controlled observation is trial `issue43-water-entry-06` (240 rows, 199 equal counter brackets; unequal brackets are retained and not used as stable event samples; trace SHA-256 `F23ED48BE712456F4F2059FA9AAD68FF6B82A40A34ABA1BBDB96F024B990A70D`). It began at `(-1172.9805,260,4048.7637)` on floor type 0 with water level -11000. At sequence 189 / counter 25729, Mario was at `(44.335144,284.77682,4222.0557)` over floor type decimal 19 (`0x13`) with floor normal Y `0.54986995`; A/B/Z were not pressed, directional stick rawY was 127, input magnitude 64, derivedInput 9, and intended yaw 14917. The action changed from `0x04000440` to numeric `0x008C0453` while forward speed became `-10.684373` and X velocity `-10.648132`. Over the next samples he moved back down the ramp with negative forward speed, returned to default floor type 0, and reached `(-184.84908,260,4213.0117)` at sequence 211 / counter 25750 in numeric action `0x00000386` with zero speed. No wall pointer was present. The trajectory matches the exact-ROM type-`0x13` → floor-class `0x13` mapping and the corresponding walking-class consumer; it is direct runtime evidence of backward sliding on this steep, very-slippery floor, not evidence of swimming or a wall collision.

Trials `issue43-water-entry-01` and `-02` made short progress but did not reach the water box. Trial `-03` remained stationary for 3,415 samples at `(-1210.3477,260,4043.456)`. Trials `-04` and `-05` stopped after the wake pulse because the initial driver used an incorrect UTC conversion; they are retained as failed attempts and are not used for movement claims. Trial `-06` reached the steep `0x13` ramp before the glide carried Mario back downhill. Review found the driver's hashtable access bug caused every active pulse in `-06` to resolve to AnalogUp; accordingly this run is evidence of that bounded uphill-input trajectory and is not credited as a completed feedback-route execution. A corrected driver revision exists locally but was not replayed. The local traces contain sanitized scalar telemetry, not raw RAM or copyrighted assets. The input helper records key edges/timestamps in `tools/issue11-local/issue40-project64-input-log.jsonl`.

Static collision navigation identifies water box 1 as X `[1024,8230]`, Z `[-58,8137]`, level `-81`; a collision-mesh sample at `(2048,4038)` found an upward floor candidate near Y `-347.725`, sufficiently below the candidate swim-entry threshold `waterLevel-100`. The feedback driver is bounded to waypoints `(0,4200)`, `(700,4160)`, `(1700,4070)`, `(2048,4038)`, with fresh-camera-yaw feedback and at most 25 300 ms movement pulses. No health fields are written. The `-06` route encountered the `0x13` ramp and slid downhill before approaching box 1; there is no runtime swim transition in this evidence.

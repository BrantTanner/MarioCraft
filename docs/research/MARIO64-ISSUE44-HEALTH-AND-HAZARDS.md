# Mario 64 issue 44: health, damage, falls, healing, and hazards

Status: bounded target investigation with representative runtime captures. Verified behaviors are separated from candidate paths and untested thresholds. The capture answers the health updater, burning-floor damage, submerged health loss and recovery, death/respawn recovery, coin-heal accounting, and a no-damage fall interval. It does not dynamically exercise every source of damage or every pickup.

## Target and method

Target ROM: Super Mario 64 (U), rev 0, 8 MiB, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. Runtime was Project64 `3.0.1.5664-2df3434`, executable SHA-256 `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`, with N-Rage range 100, dead zone 5, Real N64 Range on. The ROM and emulator are local analysis copies.

Ghidra 12.1.4 read the ROM copy without modifying it. For code ranges within the validated map, `PC = 0x80245000 + ROM offset`, ROM offsets `0x1000..0xE855F`. The report gives start-inclusive contiguous ROM envelopes from each function entry PC through the highest body byte, inclusive, and SHA-256 over that full envelope. Ghidra noncontiguous body-byte counts are not used as envelope lengths. Each mapped range is checked against `PC = 0x80245000 + ROM offset`; data outside the validated map is not extrapolated. The `FUN_...` names identify target PCs, not source names. Decompiled control flow was checked against raw instructions for the unusual fall branch described below. Data symbols outside this map are left symbolic unless an independent runtime-to-ROM block match is documented, as for the fall thresholds.

Runtime reads used external `OpenProcess(PROCESS_QUERY_INFORMATION | PROCESS_VM_READ)` and `ReadProcessMemory` only. No game-memory writes, cheat codes, ROM patches, or state mutations occurred during captures. The process-specific RDRAM base, process identity, executable/ROM hashes, and emulator profile were recorded per capture. The sampler reads the loop counter before the other fields and again after them; matching pairs are useful consistency evidence but do not make a sample atomic. The per-trial manifest identifies each sampler version and its field set, because the early lava run predates timer sampling. Unequal pairs are retained in the event extract. Project64's loop counter is not a universal physics-frame clock.

The verified MarioState fields used here are health `+0xAE`, pending hurt ticks `+0xB2`, pending heal ticks `+0xB3`, and invulnerability timer `+0x26`. Health and counter meanings are corroborated by target code and runtime deltas. Face pitch `+0x2C` was sampled as a candidate in the water and fall-route runs; peak height `+0xBC` and signed invulnerability timer `+0x26` were added only in the extended drowning run. Target code corroborates these fields; the early runs did not sample them, and no health delta is inferred from them without a matching target path.

## Health model in the USA target

`FUN_80254060` (`ROM 0xF060`, full envelope length 596, SHA-256 `B9FC701F7D6DDAA3C17DB552F11135D9D987B4A6ECD56D439EA96B8795700277`) updates health when the signed value at `+0xAE` is at least `0x100`. Pending heal byte `+0xB3` adds `0x40` health and decrements by one; pending hurt byte `+0xB2` subtracts `0x40` and decrements by one. Health clamps at `0x880`; values below `0x100` clamp to `0xFF`. Runtime observed the `0x880` cap and `0xFF` low-health sentinel. The code is signed around the health threshold; `0xFF` is a state sentinel, not ordinary zero health. The HUD export `FUN_8024B13C` stores the display count at global `0x8033B266`: health below 1 maps to 0; otherwise `(u16 health >> 8)`, so `0x880` displays 8 segments. This is a display projection, not a linear HP normalization.

When neither queued counter is active, updater conditions govern ambient changes. In water action flag `0x2000`, if Mario Y is below water level minus 140, health loses one per update, or three on terrain class 2. At/above that depth threshold, non-snow water restores `0x1A` per update. A separate poison-gas path directly subtracts four health per updater iteration when gas state is active, its transition/queued-counter gates permit it, and Mario lacks metal-cap flag `0x4`. Action and global state gates apply; this is not a global “water always heals” or “gas always hurts” rule. The runtime below confirms the non-snow branch. Terrain-specific values and branch gates come from the target updater, not source alone.

### Exact hazard and landing paths

`FUN_802507FC` (`ROM 0xB7FC`, full envelope length 320, SHA-256 `FADDFD232507344B53E1F18B414C0C14F4D77DF89AAC71407A28E1F587058795`) dispatches the floor-type handler only when action bits `0x800` and `0x2000` are clear. For type 1 it calls `FUN_8025065C` (`ROM 0xB65C`, full envelope length 200, SHA-256 `0994CF3AF657AE36A7FE11D917A877B2006211C9A8D02075A2A9B4A6DB1F0226`), which additionally requires action bit `0x10000` clear and Mario Y below floor Y plus 10. If Mario flag bit `0x4` is clear, it queues 18 hurt ticks when flag `0x10` is clear, or 12 otherwise, then calls the burn action path. The runtime saw the repeating health decrement and action `0x010208B7` while on that floor.

`FUN_8026A224` (`ROM 0x25224`, full envelope length 476, SHA-256 `84DA1620584B97C66CD0CB2DC658EB6922D6A38B22674016DEA2A8A36D731AC4`) is the fall/landing helper. It computes peak-height minus current Y, requires vertical velocity below `-55`, action not equal to `0x108008A4`, and floor type not equal to 1. Above `DAT_80336C08` (`3000.0`) it queues 16 hurt ticks when flag `0x10` is set, otherwise 24. For the lesser branch, delta must exceed `DAT_80336C04` (`1150.0`) and `FUN_80251BD4(m)` must return zero; it then queues 8 ticks when flag `0x10` is set, otherwise 12, and sets `+0xB4=0x1E`. Values came from a guarded read-only RAM probe and a unique 64-byte match to ROM `0xF1BF0`, not a global address extrapolation. The target code compares the 16-bit action state at `+0x18` against `0x008008A9`. Raw instructions at PC `0x8026A250..0x8026A25C` form `lui at,0x0080; ori at,at,0x08A9; lhu t8,0x18(t7); bne t8,at,...`; a zero-extended halfword cannot equal `0x008008A9`, so the branch selecting `600.0` is unreachable in the shipped USA code. `FUN_80251BD4` (`ROM 0xCBD4`, full envelope length 296, SHA-256 `FABC0B8568ADDAB5CD902EA19C7B5F3780F6BB17A417ABB0392ABC2F82036B83`) is the additional lesser-branch zero-return gate. The 64-byte data block at ROM `0xF1BF0` uniquely matches the read-only runtime RAM block and has SHA-256 `7825CF946D486511EADFDAB5FFAF694EEE01A357EC563B3B505209AA1F5EC8CB`; its floats at offsets `+0x14/+0x18` are 1150.0/3000.0. Do not “repair” the shipped comparison when reproducing behavior.

`FUN_8026A12C` (`ROM 0x2512C`, full envelope length 248, SHA-256 `AB4BB8C97723AB4DC56E92F117035625A3ED5EE57F3B3AF6F1C7ED455454303A`) is a wall-type-1 burn helper, not the fall helper. It uses collision normal and speed gates and queues hurt ticks. `FUN_8026CD0C` and `FUN_8026CE50` (`ROM 0x27D0C`, full envelope length 324, SHA-256 `E417F0A5EB998B34CD4A0F69C0205D7C233B7CA73E34649B33A3D57A08431D1F`; `ROM 0x27E50`, full envelope length 216, SHA-256 `B3DB2FF4A0E98BA616786B3ED5F2E88A8FC2837495180F615384AC482F60514E`) are burning-action handlers that directly subtract 10 health and clamp at `0xFF`. The deep-water trace does not execute these handlers.

## Repeatable local scenarios

Use the analysis copy and isolated Project64 build listed above. Load the local courtyard state `tools/issue11-local/issue35-mario-gameplay-baseline.pj.zip` for water testing or lower-platform seed `tools/issue11-local/issue41-lower-platform-y803-z2670.pj.zip` for the bounded fall trial. These states are local-only and are not published. Start a uniquely named `issue44-...` capture with the external read-only sampler and record its metadata before input. Use the reviewed Project64 input helper, which validates the foreground process and releases held keys in `finally`.

For water, reach the lake at surface level, then hold A+AnalogUp briefly to dive and A+AnalogDown to rise. Keep the face-pitch and health sampler active; verify actual Y against `waterLevel-140` and the sampled floor before interpreting a health change. For drowning, start a fresh capture, dive to the bottom and allow the sampler to record death and the complete post-respawn heal. For the lava surface, enter Lethal Lava Land normally from the castle painting, touch the broad lava floor and let the capture continue through death/respawn. Do not use cheats or alter health fields. For a fall baseline, load the named lower-platform state and use a bounded walk-off; the approximately 139-unit fall here is known to be non-damaging only.

The event extract and local trace IDs provide deterministic comparison points, not a requirement that a different run reproduce the same world position or sample number. The manifest records each raw trace and metadata hash locally, the exact sampler version, observed input holds, and the input-log hash. The state-load identity was not recorded per capture; replay seed files are listed as references, not asserted as the states used. A stable capture must retain the full raw local JSONL and metadata until event extraction is validated; publish only sanitized selected events.

## Acceptance audit and limits

- Health fields, queued counters, updater, cap, low-health sentinel, water thresholds, lava floor helper, action damage, death/respawn transition, coin healing queue, and fall/landing code are tied to the exact USA target.
- Runtime evidence covers a lava contact sequence through health sentinel and respawn recovery, submerged health loss through death/respawn recovery, resurfacing recovery and cap, and a bounded no-damage fall.
- Equal and unequal counter pairs are retained in the selected event extract. An equal pair is not asserted to be an atomic sample.
- The damaging-fall branch, controlled invulnerability re-hit, coin/recovery-heart pickup, gas, cap-specific effects, and individual course death barriers were not dynamically isolated. Static fall thresholds, timer gates and call paths are target-derived; the report avoids claiming those runtime observations. Snow-water behavior and enemy-specific contact remain untested.
- Crossover recommendations for architecture #18: preserve the target integer health cap `0x880`, death sentinel `0xFF`, and queued `0x40` updates; schedule health and invulnerability counters on the emulated Mario-update cadence rather than assuming one Minecraft tick per physics frame; convert water depth 140 and fall thresholds 1150/3000 through the chosen world scale while retaining velocity, action, floor and `FUN_80251BD4` gates; map Minecraft damage to pending hurt/action/invulnerability behavior rather than writing Minecraft health directly; keep coin, heart and cap pickups outside the initial MVP while retaining explicit default cap state; hand death/respawn to issue #28 while preserving world and life policy separately. Issue #43 owns surface classification/geometry, and this report consumes its type-1 lava classification. The damaging-fall, controlled re-hit and pickup interactions remain possible bounded follow-up investigations.

# Mario 64 issue 48: model, skeleton, animation, and rendering path

Status: bounded target and runtime research complete; awaiting independent review. This establishes a representative Mario player-model path, selected animation states, one geometry/material/texture chain, and the target graphics-task handoff. It is not a full asset catalog, complete actor/course inventory, or full RSP/microcode study; those are covered by issues 15 and 16. Title/menu camera ownership remains unresolved from issue 47 and should be completed with UI work in issue 49.

## Target and method

Target: USA rev 0, 8 MiB big-endian ROM, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. Project64 3.0.1.5664-2df3434 SHA-256 `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`. Runtime reads used guarded read-only process memory access. Sampler rows are bracketed by the main-loop counter; matching counters do not guarantee atomicity. No ROM, decoded asset, screenshot, raw RAM, or save-state data is included. The accompanying inspector reads the ROM supplied by the operator, verifies its whole-file SHA, decodes the MIO0 bank in memory, and prints scalar offsets, command fields, and hashes only.

Address evidence uses unique whole-block ROM matches for non-linear mappings and the validated `PC = 0x80245000 + ROM offset` mapping only in ROM `[0x1000,0xE855F]`. Full function envelopes include internal gaps. Source labels refer to `n64decomp/sm64` at `9921382a68bb0c865e5e45eb594d9c64db59b1af` for navigation; target bytes, runtime segment pointers, and unique ROM matches are the evidence.

## Asset loading and Mario geometry

The target level-script interpreter (`FUN_803805C8`) dispatches command records. The 256-byte level-script command table at guest `0x8038B8B8` uniquely matches ROM `[0x108638,0x108738)`, SHA-256 `ADD18E0B340AD85C2F64EC537BA4560352E87203FF882315C318AD07E262FD21`. Its selected entries dispatch opcode `0x17` to `FUN_8037ECA4` (PC `[0x8037ECA4,0x8037ECF8)`, ROM `[0xFBA24,0xFBA78)`, 84 bytes, SHA-256 `D38E7A0ADBDC19FEB7D321AEB6592C6009CA81CD4644E3866FFC250392A238D2`) and opcode `0x18` to `FUN_8037ECF8` (PC `[0x8037ECF8,0x8037ED48)`, ROM `[0xFBA78,0xFBAC8)`, 80 bytes, SHA-256 `C7D58F67CDD4FF265BC11BDC623E86CE40C9BEC4DAF35A0354ED83E48AB9BA9A`. Opcode `0x17` invokes the raw DMA loader; opcode `0x18` invokes the compressed loader `FUN_802787D8` (PC `[0x802787D8,0x802788B4)`, ROM `[0x337D8,0x338B4)`, full envelope 220 bytes including an 8-byte gap, SHA-256 `239150A9914575850464122EED68FC7A38B5D93FD1128D7F816A573F43F0B634`), which reads the MIO0 output size, decompresses, then sets the segment base. At ROM `0x2ABCA0`, opcode `0x18`, length 12, loads segment 4 from ROM `[0x114750,0x1279B0)`; the record at `0x2ABCB8` uses opcode `0x17`, length 12, to map the raw GeoLayout bank `[0x1279B0,0x12A7E0)` to segment `0x17`. The next level command at `0x2ABCE0` is opcode `0x22`, length 8, model ID 1, GeoLayout pointer `0x17002DD4` (Mario model under the pinned navigation labels). These are distinct from the GeoLayout command interpreter `FUN_8037E0B4` and its command handlers.

The compressed segment-4 source is 78,432 bytes, SHA-256 `EF621DBA1B29D022F4FE7E3A2FA9990F9935F79CB89A6C572DFE39523F9D1F45`. Its MIO0 header gives output size `0x35378`, compressed-data offset `0x19D4`, and raw-data offset `0xAED0`. In-memory output is 217,976 bytes, SHA-256 `2FB26A131C645493A884642360E6355FB4EEE2C5C4B2C205624D2008CDBAC1C4`; a guarded Project64 read of live segment 4 matched the entire decoded output at KSEG0 virtual guest range `[0x8007EC20,0x800B3F98)` (physical RDRAM offsets `[0x7EC20,0xB3F98)`) with that hash. The segment resolver `FUN_80277F50` maps the level-loaded segments to guest pointers; the Mario GeoLayout pointer resolves to `0x800EA0A4` in the sampled run.

The 92-byte Mario root record at ROM `[0x12A784,0x12A7E0)` (SHA-256 `67C073F982ACFF19B7536E7CAD43D1A3E11C43D684C705DE307DEB416AAC76C0`) branches at `0x12A7B8` to segmented pointer `0x17002CE0` (load-body path), at `0x12A7C0` to `0x17002D7C` (render-body path), and the high-poly load-body branch at `0x12A69C` points to `0x1700053C`. The latter resolves to segment-17 offset `0x053C`, ROM `0x127EEC`, the Mario body GeoLayout. Segment-17 raw bank hash: SHA-256 `00C0DD666AD42E3034762DE5440E0AC933787458DE9117C2049990BC3AABD3C3` for 11,824 bytes.

## Animation data and observed transitions

Mario state points to a Mario object at `+0x88` and an animation-list wrapper at `+0xA0`. Setter `FUN_802509B8` (PC `[0x802509B8,0x80250B04)`, ROM `[0xB9B8,0xBB04)`, 332 bytes, SHA-256 `9FB7A9870A758651FCE93DF24E9F278F9954D079BC239816EAE2ACF791E29EFB`) and scaled variant `FUN_80250B04` (PC `[0x80250B04,0x80250C7C)`, ROM `[0xBB04,0xBC7C)`, 376 bytes, SHA-256 `8555D11D223B9BBA0D2A4A17A637981D7E33B529E7D20AE444D33D2B3EE2DE96`) select the animation and patch its values/index pointers. The object fields set include animation ID `+0x38`, animation-Y-translation at `+0x3A` (the executed sampler v1 called this `animationState`; target setter dataflow shows it copies MarioState `+0xB0`, so it is not action state), animation pointer `+0x3C`, current frame `+0x40`, and acceleration `+0x48`. A representative target payload header has signed 16-bit fields flags/divisor/start/loopStart/loopEnd/count at `+0/+2/+4/+6/+8/+0xA`, then values/index offsets at `+0xC/+0x10` and byte length at `+0x14`. The sampled headers have count value 20, a signed-16 values array and an index stream; the pinned source struct labels the +0xA field unusedBoneCount, so its semantics are left conservative here. Target `FUN_8037C7D8` consumes 4-byte index records as unsigned-16 frame-limit/value-offset pairs, advancing the cursor by four; it returns `valueOffset+frame` below the limit and `valueOffset+frameLimit-1` at or beyond the limit. This is bounded evidence for the channel sampler, not a complete decoder for all animation variants. The target end predicates compare current frame with header loop-end `+8`.

The level-script interpreter `FUN_803805C8` occupies PC `[0x803805C8,0x80380684)`, ROM `[0xFD348,0xFD404)`, a 188-byte full envelope including an 8-byte gap, SHA-256 `4C9960F45C1C124445D650355ED8391E13504B5C0C42B99C34E78F6E403DFD9D`; it dispatches level commands, invokes `FUN_8027B3B4` for area rendering, and finalizes the display-list task. `FUN_8027B3B4` traverses the area graph through `FUN_8027E130` and invokes HUD/UI paths; `FUN_8037E0B4` is the separate GeoLayout interpreter used while constructing/traversing graph nodes. `FUN_80247D14` finalizes display-list task fields. `FUN_80247B3C` builds a type-1 graphics task descriptor containing boot microcode, microcode, microcode data, DRAM stack, output, display-list start/size, yield buffer, and message queue. `FUN_80246C10` queues the graphics task; scheduler `FUN_8024651C` selects graphics/audio work and calls `FUN_80322A5C` to submit it.

The descriptor also contains code/data addresses and lengths, but this function alone does not prove the actual code/data transfers or full task completion semantics. ## Bounds and follow-ups

This evidence covers Mario and representative assets from one loaded bank. It does not catalog all Mario parts, alternate costumes/materials, nonplayer actors, course geometry, or every animation. Texture candidates without direct display-list references remain labeled candidates. Issue 15 owns the broader asset catalog and issue 51 the reusable decoder/loading workflow. Issue 47's Area Camera findings concern game-state camera objects; title/menu camera ownership and UI-specific render state remain unresolved for issue 49. No claim is made that its Area Camera table describes the whole application.

# Mario 64 HUD, text, menus, and presentation UI (#49)

## Scope and result

This dossier inventories the HUD/text/menu paths needed to plan a bounded reconstruction of Super Mario 64 USA rev 0 (8 MiB; ROM SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`). It covers the ordinary gameplay overlay, text, notification, and screen-text record paths, pause state, distinct title and file-select camera paths, the live file-select overlay/controller path, and static course/result dispatch. It is a bounded feature catalog, not a frame-by-frame inventory of every title, course, cutscene, save, or language screen.

The render pipeline separates world scene graphs from screen-space overlays. For gameplay, area renderer `8027B3B4` draws the current graph and then calls `802E3D2C`, which establishes the HUD orthographic pass and dispatches HUD bits. Pause and menu screens use their own presentation state. The #10 title-screen RDRAM fixture and a separate live SELECT FILE scene show different camera owners: the title custom-model path selects a type-`0x200` camera; the live file-select graph has a fixed-field type-`0x114` camera. The current file-select callback code matches the pinned ROM; its controller polling is traced statically, while only the Start transition into the screen was exercised at runtime.

## HUD data and visible branches

`8024B13C` writes these signed/unsigned 16-bit values into the aligned 12-byte block at `8033B260` when its HUD gate `8032DDD0` permits an update:

| Offset | Field | Source / behavior |
|---:|---|---|
| `+0` | lives | Mario state `+0xAD`, sign-extended from S8. |
| `+2` | displayed coins | Animated display count; increments toward Mario state `+0xA8` on alternating loop-counter steps rather than copying it directly. |
| `+4` | stars | Mario state `+0xAA`. |
| `+6` | health wedges | Mario health `+0xAE` shifted right 8; the detailed health semantics are in #44. |
| `+8` | keys | Mario state `+0xAC`, sign-extended from S8. |
| `+0xA` | HUD flags | U16. The function sets coin-related bit `0x0002` from `8033BAC6` and damage-related bit `0x8000` from hurt-counter state. Other bits are dispatched by `802E3D2C`; bit names are not inferred beyond code-supported branches. |

The `802E3D2C` HUD branch table calls: `0x01` lives renderer `802E3744`; `0x02` animated coin-count renderer `802E37A8`; `0x04` star renderer `802E380C`; `0x10` repeated key renderer `802E38E4`; `0x08` health/power-meter update path `802E3654` and additional icon/display-list path `802E3B3C`; and `0x40` time-derived display `802E395C`. `802E3B3C` reads `80332608` through masks `0x07` and `0x18` and selects entries from a texture/list table; its visible icon meaning is unresolved. `802E395C` derives `/1800`, `/30`, and `/3` components from `8033B26C`; no separate score label is proven. With flags zero, it resets meter state (`803325F0=0`, `80361440=8`, `803325FC=0`). The dispatcher also checks the Area+`0x24` camera mode; numeric mode 10 selects `802DB08C`, which emits four rotated display lists centered around the screen's middle, consistent with the cannon reticle observed in #47. This is separate from text/dialogue. The numeric HUD flags are internal dispatch values, not user-facing UI IDs.

## Representative runtime observation

Target runtime: Project64 portable 3.0.1.5664-2df3434 (binary SHA-256 `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`), loaded with the verified ROM above and the existing courtyard seed (`6E2C8265A8A9A19761BCC6CE29FA20694FAD5444B325B1F22CA987776A2D6DFE`). The input helper pressed Start to enter pause, then Start to resume. A separate visual read showed the pause screen overlay; the sampler measured the setter’s `8033B238` mode rather than inferring pause from an unchanged HUD.

Sanitized mode-2 pause scalar sample: `playModeS16=2`, `pauseTimerCandidateS16=0`, `lives=4`, `coinDisplay=0`, `stars=0`, `health=2176`, `healthSegments=8`, `keys=0`, `hudFlags=61`, action `0x0C000203`. The same v2 trace contains 64 mode-0 rows, including the first and last, with lives 4, displayed coins 0, stars 0, health 8 wedges, keys 0, and flags `0x003D`; this is direct normal-play-mode HUD scalar evidence, not a synchronized screenshot. Independent trace checks found 325 rows total (261 mode 2, 64 mode 0), 307 equal-counter brackets, and flags `61` throughout. Counter equality is not atomicity; advancing loop counters during mode 2 did not change the pause interpretation. The visible pause overlay is the independent UI confirmation. The in-game HUD fields can remain live/stale beneath menus and are not treated as menu-state data.

After loading the preserved pre-file-select state (SHA-256 `68EB47233F30DFE14C15116C2D937FA165585A3A78E7C50C42A6449E48F0107D`), a single Start pulse (scan `0x1C`, 120 ms) showed the SELECT FILE screen in Project64. No file slot or SCORE/COPY/ERASE/STEREO control was activated. A guarded live read-only graph probe on that same visible scene found the 10-node graph and fixed camera fields described above; the graph root and active area were stable across the probe, while the loop counter advanced. The screenshot was inspected live and not stored or published. No new file or EEPROM slot was created, and existing save data was preserved. Runtime evidence includes live HUD scalars in play and pause modes, a visually observed pause overlay, and the repeatable file-select arrival. It did not directly observe a power-meter transition, text dialogue, course-clear/result screen, erase/copy/slot selection, title attract sequence, credits, or settings screens.

The title and file-select camera evidence is scene-specific. The #10 title-screen RDRAM graph was followed from its root through all reachable child (`+0x10`) and sibling (`+0x08`) lists with pointer validation against the 4 MiB snapshot; its bounded traversal contains no type-`0x114` graph camera node. It has a type-`0x103` projection node and custom callback node `8016576C` (type `0x12A`, callback `802764B0`), which selects custom model/list routines including `8019C9F8`. That path obtains a view object at `80104738` and camera `800F7090` (type `0x200`), with FOV45, eye `(0,200,2000)`, focus `(0,200,0)`, roll0; `801799AC` builds eye/focus camera matrix state and calls matrix/modelview code through `8019F458`. The exact PC/ROM ranges and hashes for the eight matched blocks are in the sanitized evidence manifest. Separately, the live SELECT FILE graph has a type-`0x114` camera node with fixed fields consumed by generic handler `8027BF58`. Its 10-node traversal checked every reachable child/sibling node and verified stable graph root and active area; loop counters changed, so reads were non-atomic. Its generated overlay node callback `80176688` was read from live RAM under exact process identity and live ROM-prefix guards; its 84-byte function, `801764E0` (424 bytes), and `80173AE0` (396 bytes) each uniquely matched the pinned ROM and title snapshot. `80173900` and `80173780` also match the pinned ROM and snapshot at their exact full function ranges. The callback calls the orthographic state dispatcher and cursor path. The dispatcher has states 4–10 and `0x1C`, and queries four save-slot predicates. Cursor update reads signed S16 axes at `8032D5EC` offsets `+0` and `+2`, zeros values in `[-1,+1]`, then updates X/Y cursor scalars. State-gated controller logic reads U16 `buttonPressed` at `+0x12` and tests masks `0x5000`, `0x8000`, and `0xD000`; the matching controller updater `80248638` derives it as `newButtons & (newButtons XOR previousHeldButtons)` and copies the U16 held-button word to `+0x10`. This establishes edge-vs-held semantics from the producer code. No cursor, slot, or other file-select control was activated, so their live effects are unobserved. This anchors a concrete file-select overlay and controller polling path without assigning meaning beyond traced branches.

## Reproduction and safety

1. Use the pinned USA rev-0 ROM and the existing known courtyard save seed. Verify the Project64 binary and ROM SHA-256 values above.
2. To observe the gameplay HUD, load the known seed and wait for ground-idle. Capture only the aligned HUD block using `mario64-issue49-external-capture.ps1` (SHA-256 `52D18AAEDA9FD8321F33CA2560E3F349EFFB710E38CA4411D1D9E6E7D72D5CA6`).
3. Press Start once to pause, visually confirm the pause overlay, and capture using the v2 helper `mario64-issue49-external-capture-v2.ps1` (SHA-256 `3E69CA5257711541B3A104D4BBE5D2EE4C8BC393E8D550AECDB483F41A7DC790`). The helper checks process identity, live ROM signature, base and aligned widths; it reads only process memory and writes local trace rows. Press Start to resume and confirm signed play mode returns to 0.
4. The file-select screenshot is a local observation only after preserving the current EEPROM/save state; no copy/erase action is needed to inspect its visible controls. Keep any captures/screenshots/state files local.

No raw RAM traces, RDRAM snapshots, screenshots, ROM bytes, decoded UI assets, emulator states, EEPROMs, or save files are included in publication. The evidence manifest carries sanitized code hashes, tool hashes, and scalar pause observations only.

## MVP boundary and non-MVP bounds

# Mario 64 issue 51: private decoder and local asset loader

Status: local workflow validated and independently reviewed for publication. Research only; no gameplay code or prototype was produced.

## Reproduce locally

Use the supplied private 8 MiB big-endian Mario USA rev 0 ROM, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. The validated source-only script is published under `docs/research`. From the MarioCraft repository root, run:

```powershell
py -3.13 .\docs\research\mario64-issue51-local.py `
  '<private verified ROM path>' `
  --output .\tools\issue11-local\issue51-decoded\run-1
```

The script verifies the ROM's byte order, size, and full SHA-256 before decoding. It refuses output paths outside `tools/issue11-local/issue51-decoded`; the repository `.gitignore` ignores `tools/`. Use a new child directory for each run. The Python workflow uses only the standard library and has no package installs or external asset inputs. Optional `--validation-fixture` accepts a private scalar-only audit file; ordinary reproduction does not need that file.

This was run on Windows 11 with PowerShell 7.6.5 and Python 3.13.15. The source-only script contains ROM offsets and scalar expected hashes, but no ROM bytes, asset payloads, decoder-generated bytes, pixel colors, vertex coordinates, or sampled animation values. The validated script SHA-256 is recorded in the final execution manifest.

The run writes a 32×32 RGBA PNG, a bounded OBJ mesh, a GeoLayout skeleton subset JSON, animation-114 JSON, and two WAV previews. It then reloads the PNG with chunk CRC and decompression checks, parses the OBJ vertex/UV/normal/face references, reloads and bounds-checks the skeleton and animation JSON, and reads both WAV files through Python's `wave` module. A separate Pillow 12.3.0 loader under Python 3.12.14 independently reopened the PNG as 32×32 RGBA and matched its decoded pixel-buffer hash. These checks cover actual local loading and format bounds; the generated files and every decoded asset remain local and private. Workflow source SHA-256 for the final executed version is `12F8B0BE847A00287B30412D1741E04824BA0122FF626F2DB98AE8FA9374C871`.

## Exact target inputs and decoder checks

The input ROM is the USA rev 0 copy identified above. The existing #48 investigation established ROM `[0x114750,0x1279B0)` as the level-loaded MIO0 segment-4 bank; the script decodes it to 217,976 bytes with SHA-256 `2FB26A131C645493A884642360E6355FB4EEE2C5C4B2C205624D2008CDBAC1C4`. That output hash matches the complete live Project64 segment-4 read already recorded for #48. The raw Mario GeoLayout bank is `[0x1279B0,0x12A7E0)`, 11,824 bytes, SHA-256 `00C0DD666AD42E3034762DE5440E0AC933787458DE9117C2049990BC3AABD3C3`.

The material path selects a 2,048-byte texture span at decoded segment-4 offsets `[0x1090,0x1890)`, SHA-256 `1BEBDBC8AC4921C0A38852CC640FB531AAD64E82A047791CF40648EE27667559`. Its target display-list fields identify RGBA16, 32×32, and a 1,024-pixel load. The local decoder converts those words to a standard RGBA8 PNG. Independently reviewed texture coordinates are checked by a digest over the selected scalar pixel fields; individual pixel values are not emitted.

The first bounded mesh batch uses 15 16-byte vertex records from segment-4 offsets `[0xC090,0xC180)`, SHA-256 `DEE91D706F0875AABC1ECBECEC4413AEED01C770685D23AFFADFC744AB8F8DB8`. The display-list span `[0xCA00,0xCC98)` is 664 bytes, SHA-256 `692A5C0FEA7CAA08D6435965EF4FAFE6DA7910EFD157D0693388293FFD7B686B`; its first vertex-load command and six following triangle commands resolve within that selected batch. The local OBJ contains only those first 15 vertices and six faces. Coordinates and pixel values are checked against independently selected private fields and only their canonical-field digests are reported.

The selected GeoLayout subtree is ROM `[0x127EEC,0x127F50)`, 100 bytes, SHA-256 `19A639705B8B779A388B9FE753B9B73D0C7544869068CE1C6F13BC9502374805`. The decoder recognizes only the target-verified command boundaries in that window, extracts a root animated part, the butt part, an intervening rotation node, the torso part, and one torso child, and preserves their hierarchy in private JSON. Ghidra target handler checks corroborate animated-part opcode `0x13` at PC `0x8037DB74`, ROM `[0xFA8F4,0xFA990)`, 156 bytes, SHA-256 `B1A57886005C6A165A84B5A7D9517D3D5D1C356EC855D97A60C9090D4B9A326C`; rotation opcode `0x12` at PC `0x8037D998`, ROM `[0xFA718,0xFA7DC)`, 196 bytes, SHA-256 `0DB27C4D6B30D41BA25F941C6A330131EA4221577AB07585CAFCD1342CD404A3`; callback opcode `0x18` at PC `0x8037DE34`, ROM `[0xFABB4,0xFAC14)`, 96 bytes, SHA-256 `39655955F726AD5689ACBC2F41C114F90536EF70017B825905EB426B459A868D`; and the rotation argument reader at PC `0x8037CBFC`, ROM `[0xF997C,0xF99E4)`, 104 bytes, SHA-256 `52E81D7DC259B79FAF4C9D8953E21774843C4F2214FE34FD70ABF2014E60E5FD`. The selected open-node instruction window PC `[0x8037CFC0,0x8037D010)` (80 bytes), SHA-256 `9032D549A28A1D02BD7B82607B83041A330EBA65CDB75429AC5125C135E05B7D` increments node-stack depth and advances four command bytes; the close-node window PC `[0x8037D018,0x8037D048)` (48 bytes), SHA-256 `B1D59A96F69C5B24DFB23960B3D38E4FC1CB164EF90382CDF72DB1F3EA1C5EC6` decrements depth and advances four. These two ranges are manual instruction windows, not named Ghidra functions. A graph-attach helper at PC `0x8037CC74`, ROM `[0xF99F4,0xF9AE0)`, 236 bytes, SHA-256 `3640EC647561882F5CB15641AFB88D71968702FA59226DA1687B4F6FEA60CB52` was checked too. All seven target ranges are whole-block unique ROM matches. The subtree includes two callback commands whose pointer words are left uninterpreted and a final branch whose destination is not expanded. The local reload checks the five-node parent chain; no joint translations or display-list command data are printed.

Animation ID 114 is ROM `[0x53F138,0x54035A)`, 4,642 bytes, SHA-256 `91473B0B32A6326CC2AC0DBF019DEAD837C9270F50ECC77C0A6235720FFF995B`. Its private decoded structure has a 24-byte header, 63 bounded index/value channels and 2,171 signed values. Six independently selected channel/frame checks match the private root audit by canonical-field digest. The target channel sampler clamps a frame at or beyond a channel's count to that channel's final value; this does not infer animation-loop or playback timing.

The audio decoder accepts the bounded VADPCM order-2 format documented by Nintendo's N64 tool manual: 9 encoded bytes per 16 decoded samples, with predictor-book metadata. The local Python decoder is an adaptation of the pinned `depp/vadpcm` arithmetic (commit `413d52043a928c5fac066ccda1e69b73c7f7132b`), with a separately compiled C implementation from that same pinned source used as an oracle. Exact source files are `codec/decode.c` (3,013 bytes, Git blob `8f57ec296973d5ceb3107b085863545578973c6e`, SHA-256 `C03BB813209667F733628E7A91F72FCB200AD7A565778017C135EEA1EB0B1A18`), `codec/vadpcm.h` (9,052 bytes, Git blob `24161626f46ecbe46d0ee166e608daa5b340a0a4`, SHA-256 `43262C330980946E845B4FD7A5DC5C86B359E70731B880C68614E9146C6FB61D`), and `LICENSE.txt`. Fetch those pinned files into a private directory from `https://raw.githubusercontent.com/depp/vadpcm/413d52043a928c5fac066ccda1e69b73c7f7132b/codec/decode.c`, `https://raw.githubusercontent.com/depp/vadpcm/413d52043a928c5fac066ccda1e69b73c7f7132b/codec/vadpcm.h`, and `https://raw.githubusercontent.com/depp/vadpcm/413d52043a928c5fac066ccda1e69b73c7f7132b/LICENSE.txt`. The compiled DLL has SHA-256 `75A1E9DB2AD44239B3CAA06E81DEFD1D1A7D3BF44BA3584E5D0947488738A753`. Its compiler reports MSVC 19.50.35720.0 x64 (toolset directory 14.50.35717); flags were `/std:c11 /O2 /LD /Drestrict=__restrict`. Enter the x64 MSVC developer environment with `vcvars64.bat`, then run `cl /nologo /std:c11 /O2 /LD /Drestrict=__restrict /I. codec\decode.c /link /EXPORT:vadpcm_decode /OUT:vadpcm-oracle.dll`. From the MarioCraft root, run the sanitized helper `py -3.13 docs\research\mario64-issue51-audio-oracle.py ROM --dll PRIVATE_ORACLE_DLL`; it verifies the ROM identity and prints scalar hashes only. The helper contains no game bytes, and the upstream MPL-2.0 license and notices are preserved in the private ignored oracle directory. No upstream decoder source or binary is vendored in these public files.

Instrument 0 follows bank-control entry 0 `[0x57B860,0x57BC80)`, sample record `[0x57B890,0x57B8A4)`, predictor book `[0x57B8B0,0x57B8F8)`, loop record `[0x57B900,0x57B910)`, and sample data `[0x5936A0,0x593D8E)`. Sample data is 1,774 bytes (SHA-256 `D6D58E52B91976C735A29EE344260F85CA0B785EFF118758282DC586C45359F0`). The decoder consumes 197 complete frames (3,152 samples) and leaves the single trailing byte unconsumed. Its PCM hash is `EA7849B2B490E402B2C5A24FED4AD3382E161CF17EA5724A57B67524C35F1941`, matching the independent C oracle. The loop end is 3,153 samples, so this resource still has a one-sample end mismatch; no byte or sample is fabricated to conceal it.

Instrument 2 follows sample record `[0x57B9B0,0x57B9C4)`, predictor book `[0x57B9D0,0x57BA18)`, loop record `[0x57BA20,0x57BA30)`, and sample data `[0x596660,0x59698A)`. Its 810 bytes (SHA-256 `CFCB907835F9B94FE42152043D34F4D676D2B0C5A3F85AC47FCB1A29DA0CC8C3`) decode to 90 complete frames / 1,440 samples, matching its loop end exactly. PCM SHA-256 `82047EE03497C63DFDB80EB1254D85B76A82B080EB128978F6739A22F47F69C2` matches the independent C oracle. WAV preview files use 22,050 Hz as an explicit local container choice; exact instrument playback rate was not established.

The `vadpcm_dec` manual describes the decoder as producing raw mono 16-bit PCM. The related encoder manual defines the codebook and single loop point. The pinned `depp/vadpcm` implementation provides the algorithm reference and the compiled C oracle for byte-for-byte PCM hash checks. The target-derived relationships and bounds come from the #48/#50 reports and selected ROM bytes, not source-navigation labels.

## Remaining format coverage

This is a finite representative decoder set, not the complete #15 asset catalog:

- Texture conversion covers only the selected RGBA16 32×32 image; CI, IA, I, YUV, palettes, mipmaps, and texture-animation forms are unsupported.
- Geometry conversion covers the first selected vertex batch and six triangles; other vertex formats, subsequent mesh batches, display-list state, and full model assembly are unsupported.
- GeoLayout loading covers the five selected nodes and the listed command widths; unknown commands, branch targets, other skeletons, and complete GeoLayout traversal are unsupported.
- Animation loading covers ID 114's header, bounded channels, and scalar values; other animation IDs, runtime blend/interpolation state, motion playback, and complete state coverage are unsupported.
- Audio decoding covers order-2 VADPCM with two predictors. Instrument 0's one-byte tail/loop-end difference remains unresolved. Other codecs, stereo, full sound banks, sequence bytecode, sample-rate/pitch reconstruction, effects, and audible runtime output are unsupported.

No new Project64 capture was needed: #48 already matched the complete decoded segment-4 bank against its live read, and #50 identified the audio sample/resource ranges. These are exact-ROM and prior runtime findings; the PNG/OBJ/JSON/WAV files are local decoder outputs, not game-runtime captures.

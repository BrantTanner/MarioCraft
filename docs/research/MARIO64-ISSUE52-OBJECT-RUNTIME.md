# Mario 64 object runtime and lifecycle (#52)

**Status:** reviewed research result for #52; parent issue #14 remains open. This documents the USA ROM identified in #10, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. Addresses below are target virtual addresses. The verified main-code mapping is ROM `[0x1000, 0xE8560)` to PC `[0x80246000, 0x8032D560)`; mapped ROM offsets are calculated as `PC - 0x80245000`. Data outside that mapping is described only where target references and bounded runtime observations support it.

## Runtime object records and lists

The initialized pool starts at `0x8033D488`, contains 240 records at stride `0x260`, and ends exclusive at `0x80360E88`. The pool initializer at `0x8029D1E8..0x8029D323` loops indices `0..239` and clears the 16-bit active flags at record offset `+0x74`. ROM offset `0x581E8`, 316-byte envelope, SHA-256 `5BA91705A9E61F1EF68ADC6B489A41735FFD68633A0AFA91486C7120E8AB92EA`.

Thirteen active-list headers begin at `0x8033CBE0`, stride `0x68`. Separately, the free-list pseudoheader is at `0x803610F0`, with head pointer at `0x80361150` (`+0x60`); it is not the first active-list header. Confirmed record fields used by the target include: active-list next `+0x60`, previous `+0x64`; parent pointer `+0x68`; active flags `+0x74` (16-bit); behavior flags `+0x8C`; position components `+0xA0/+0xA4/+0xA8`; behavior-associated mask `+0xE0`; behavior action `+0x14C`; subaction `+0x150`; timer `+0x154`; previous action `+0x18C`; behavior cursor `+0x1CC`; behavior base `+0x20C`; and respawn/loader fields `+0x1F6` and `+0x25C`. The opcode `0x23` handler also writes two signed-halfword operands as float values at `+0x1F8/+0x1FC`; that only establishes fields used by this command, not a complete hitbox schema. These are evidenced offsets, not a claim that every field or semantic is fully mapped. In particular, the behavior action field is distinct from Mario's movement action.

The pool/list initializer and list-header initializer are `0x802C99B8..0x802C9A3B` (132-byte envelope, ROM `0x849B8`, SHA-256 `0181D01C8E63740C6A8151D9176A7FC76C8DF4FEBB7CB6C8455947F647F68376`) and `0x802C9A3C..0x802C9AD7` (156 bytes, ROM `0x84A3C`, SHA-256 `6A4D684564D62ADCF4A5D270C8CA3CF98850C44D5F7C1B00F846207D53AD1DEC`). Allocation pops/inserts through `0x802C98A4..0x802C994F` (172 bytes, ROM `0x848A4`, SHA-256 `F3F417C2D10218C80F9062CFB2E43C2C1ED74E010C393CF5D65CDAC52EC1E3E1`); active insertion maintains the doubly linked list (`next +0x60`, `prev +0x64`). Freeing unlinks and pushes through `0x802C9984..0x802C99AF` (44 bytes, ROM `0x84984`, SHA-256 `FC38A87EF16C4B7149358D749EF70F7DA0ED6B633FE12E426A05AB15EBEC4219`). Cleanup `0x802C9B68..0x802C9BFF` is 152 bytes, ROM `0x84B68`, SHA-256 `132154D1FAB3CFD931435B9A69291B163B376AB22C97BBF01B893990D7F59A5B`. When the free list is empty, `0x802C9C00..0x802C9E5B` (604 bytes, ROM `0x84C00`, SHA-256 `942CAA6C842891D991E848FD56C1F35177191D962C37E5CF6161BB373D203F6B`) selects/reclaims a candidate through `0x8029FB1C..0x8029FB67` (76 bytes, ROM `0x5AB1C`, SHA-256 `C43444D3184DB45D9E555F32E4A85A7B97E30769CE83C7E476E049A1E125E6A1`). The latter is a reclaim selector, not the pool allocator.

## Update, removal, spawning, and behavior dispatch

The per-list update at `0x8029CBC8..0x8029CD27` follows each record's `+0x60` link, makes it the current object (`0x80361160`), and conditionally runs the behavior VM at `0x80385C00`. The removal pass at `0x8029CD98..0x8029CE57` caches `next` before processing, tests active flag bit 0 at `+0x74`, optionally records respawn state unless behavior flag `0x4000` at `+0x8C` is set, then calls object cleanup `0x802C9B68`. These exact target envelopes map to update ROM `0x57BC8`, 352 bytes, SHA-256 `B3C6AE7D30279C068A3472B466724B4AC5017E8F9A86BC76F7C7CD9877A2BC8E`; removal ROM `0x57D98`, 192 bytes, SHA-256 `011D929DE47B3EE589E031FEC0E3F802F9017EC4087DB24A4F28CC4C81738E59`; respawn marker `0x8029CE58..0x8029CEDB`, ROM `0x57E58`, 132 bytes, SHA-256 `EC09F64B2BD48DEFC17C8BB1B1D779C309B5378C298BE427E1C3D4A267FB5A6A`.

The VM's distance/flag visibility-cull path sets or clears mask `0x2` at `+0x74`; this is not proof of object removal. Actual removal is evidenced when list links are unlinked and the record joins the free chain. Runtime classifications below require structurally valid active/free membership and bracket-stable samples; changes in a flag alone are not counted as despawn.

The spawn-list loader `0x8029CFB0..0x8029D1D7` copies spawn parameters, assigns behavior and respawn fields, and sets global Mario-object pointer `0x80361158` when its spawn argument bit 0 is set. ROM `0x57FB0`, 552-byte envelope, SHA-256 `E0FF344FFEA84D33697C6483E94673621C028D498ECAF52B539274166AA69105`.

The allocator/spawn routine at `0x802C9F04..0x802CA027` selects a list from the first behavior word: when its high byte is zero, it uses `word >> 16` as `listId`; otherwise it uses list 8. The target doesn't mask the shifted result, so this is the observed decode for valid inputs, not a general malformed-data sanitizer. It reads the list-array base pointer from `*(u32*)0x803610E8`, then indexes `base + listId * 0x68`; the routine writes cursor `+0x1CC` and behavior base `+0x20C`. List 12 sets active flag `0x10`. Exact envelope ROM `0x84F04`, 292 bytes, SHA-256 `1D8EC83B675D466CE24ADC7D2749F0CDE3E1DB6A5A62AEAA2BF96D4AD1E59C9B`.

VM `0x80385C00..0x80385F87` reads the current script opcode's top byte, dispatches through table `0x8038B9B0`, and continues until a handler returns nonzero; it advances the cursor and updates script timer/subaction state. A changed behavior action at `+0x14C` relative to `+0x18C` resets timer `+0x154` and subaction `+0x150`. The VM also gates native update/collision/render paths using behavior flags. The table is documented only as a 52-pointer prefix at `0x8038B9B0..0x8038BA7F` (208 bytes), not as a fully bounded table: SHA-256 `FA1ACE082B7405DA34066E00BBE8F5EA24DFA0787A800058D830E8C82D0C5AB8`, unique ROM match `0x108730`. Slot 12 points to handler `0x80384678`; it calls the function pointer at cursor `+4`, advances by 8, and returns 0. Slot 35 points to `0x8038528C`; it reads the following word as two signed halves into object fields `+0x1F8/+0x1FC`, advances by 8, and returns 0. Slot 51 points to `0x80385A60`; it reads an index from the command and clears a mask from `*(object+0x68) + index*4 + 0x88`, consuming an eight-byte command with a four-byte operand. Slot 33 points into `0x80383EE4`; the instruction sequence sets object flags at `+2` bit `0x4` and advances the cursor by 4. The VM has unique exact 904-byte ROM match at `0x102980` (SHA-256 `B4219E60EC201C95429AC0D3B748FC3E05B3BA5A6A89A4CE681987CAF56312CF`).

The current Mario behavior base `0x800EE040` was uniquely matched as a 128-byte normalized runtime window to ROM offset `0x21CCC0` (SHA-256 `4C0188D1BD8762DD26F0590AD6EBE9FAB0EE5FAE07C0D037CC7FF23F4027A3E8`). Its first six commands, parsed from the target handlers, are: opcode `0x10` at `+4` (handler slot 16, `0x8038475C`); opcode `0x11` at `+8` and `+0xC` (slot 17, `0x80384D70`); opcode `0x23` at `+0x10` with its operand at `+0x14` (slot 35, `0x8038528C`); opcode `0x08` at `+0x18` (slot 8, `0x803845E8`); and opcode `0x0C` at `+0x1C` with native pointer operand `0x802CB1C0` at `+0x20`. The opcode `0x08` handler passes cursor `+4` to helper `0x80383DBC` then advances the cursor by four; this write-up does not assign more semantics to the helper. A second opcode `0x0C` occurs at `+0x24`; its pointer operand at `+0x28` is `0x8029CA58`, the action-particle dispatcher described below. The opcode `0x0C` handler is slot 12 (`0x80384678`) and confirms indirect call from the following word and an eight-byte cursor advance. The parsed examples establish these command layouts only; other opcode semantics remain unclassified.

The repeat-observed behavior bases were also uniquely matched as exact 128-byte normalized windows: `0x800ED62C` → ROM `0x21C2AC` (SHA-256 `5A4EE0B8DEE5FE7314D60E6487A99679516FD5899D9ADB7BBEDA1E0CD351FFD8`), `0x800ED65C` → `0x21C2DC` (`A9A562A9B541CEBFCAA2DE5E98988F738C9B342F05ABE178E2278BD7749CE79C`), `0x800ED680` → `0x21C300` (`4AFBB41C0EE1569E90AAF1C7C75702184DFCA46B124AA331E3DE71AA5B742E84`), `0x800EB95C` → `0x21A5DC` (`6F5B8E51417D5D75083724E7C876F7F56D45EDE2AAE33E1BC4D874F1DA0D1093`), and `0x800EBBF8` → `0x21A878` (`EFB3F4BAB4EDACCF60004759B768D4CDEC06885D5567F8AAF556DFEC98C2DA5B`). `0x800EE040` is the sixth matched window above. The two transient-script paths parse exactly to native expiration calls: at `0x800ED65C`, opcode `0x33` at `+4` uses slot 51 and consumes an eight-byte command with a four-byte operand; opcode `0x11` at `+0xC`, opcode `0x21` at `+0x10` (slot 33, four-byte command), opcode `0x08` at `+0x14` (four-byte command passing cursor `+4` to `0x80383DBC`), then opcode `0x0C` at `+0x18` calls `0x802C2190` through its pointer at `+0x1C`. At `0x800EB95C`, opcode `0x11` at `+4`, opcode `0x21` at `+8`, opcode `0x08` at `+0xC`, and opcode `0x0C` at `+0x10` calls `0x802AAC48` through its pointer at `+0x14`. Together these handlers establish command boundaries through the native call; subsequent script contents are not cataloged.

## Bounded native behavior and particle linkage

The sampled courtyard object classes are recorded as behavior-base addresses, not guessed enemy or model names. For run/reverse captures, post-seed entries included `0x800ED62C`, `0x800ED65C`, and `0x800ED680`; these are the repeat-confirmed post-seed bases. `0x800EE53C` was present only in the seed baseline and is excluded. For ground-pound captures, post-seed entries included `0x800EB95C` and `0x800EBBF8` (list 12). These addresses describe observed records; the captures do not establish a complete class inventory.

Native particle linkage is bounded by the target helper `0x8029C9CC..0x8029CA57`, which checks a mask at parent `+0xE0`, sets the mask, invokes particle spawn helper `0x8029ED20`, then copies transform through `0x8029F0E0`. Caller `0x8029CA58..0x8029CB33` intersects action-dispatch flags with a table at `0x8032FECC` before calling the helper. The table is exactly 18 populated 16-byte records plus a 16-byte sentinel (304 bytes through `0x8032FFFB`), SHA-256 `D24C425BA484EB9F892E8BB2785C0DA08945CCE3F6BD50BB6A6E49ECFC6E37FE`, unique ROM match `0xEAECC`; adjacent bytes are excluded. Its fields used by the dispatcher are `actionFlagMask`, parent mask, type byte, and resolver selector. The values identify spawn arguments, not behavior-class names. The 18 scalar records are included in the manifest. Polling did not observe a nonzero particle mask during the ground-pound runs, so no particle pulse is claimed as directly captured.

The static spawn-to-removal path is: action dispatcher selects a table record; the parent mask gate prevents repeat emission for that bit; `0x8029ED20` resolves the behavior argument through `0x80277F50`, allocates/links via `0x802C9F04`, sets the child parent link at `+0x68`, and makes a model/graph setup call through `0x8037C448` (not treated as behavior setup); then `0x8029F0E0` copies the parent's transform. The per-list updater later applies the active-flag removal rule and returns the object to the free chain. For native lifetime corroboration, the observed courtyard behavior windows at `0x800ED65C` and `0x800EB95C` contain native calls to `0x802C2190` and `0x802AAC48` respectively; both call `0x802A0568`, which clears the active 16-bit flag at `+0x74`. `0x802C2190` clears after timer `+0x154` exceeds 4 (228-byte envelope, SHA-256 `A0362346FF3177299A13EBD6F141E05AA8C321B126CB5D9F933AB3C3D652551C`, mapped ROM `0x7D190`). `0x802AAC48` clears when its timer exceeds `0x14`, and also when its opacity-like field falls below 2 (580-byte envelope, SHA-256 `448F37CBADB3E62AB664EC4B1969E35C0BB8264085F78BAE6C8523FF1C0679B3`, mapped ROM `0x65C48`). The shared clear routine is 12 bytes, SHA-256 `76F5A6A19A82443F8CDDF7637030BEA08F5BD3F4ED5A9B9AE974A146DBCEE733`, mapped ROM `0x5B568`. This supports actual active-flag termination followed by the common removal/free path; it distinguishes that path from visibility/cull flags. These exact functions and the allocator, list update/removal, and particle helpers are hashed in the manifest. Runtime rows prove object allocation/removal and the input recipes, but do not identify any specific captured record as one of the 18 particle types.

## Repeatable Project64 lifecycle observations

Both scenarios used the same canonical courtyard Project64 F7 state, seed SHA-256 `6E2C8265A8A9A19761BCC6CE29FA20694FAD5444B325B1F22CA987776A2D6DFE`, with Mario at `(-1328, 260, 4354)` before input. The target ROM hash is above. Inputs were sent by the guarded helper in #47; it checked the expected Project64 PID/HWND and released keys in `finally`. A bounded read-only sampler captured a contiguous RDRAM snapshot with before/snapshot/after main-loop counters, object active/free membership, Mario action/position, and process/ROM/seed identity. Rows that failed structure or counter checks are excluded from lifecycle classification.

**Run and reverse.** Repeat captures `issue52-run-turn-r6` and `issue52-run-turn-r10` each used wake A, AnalogUp about 1.5 seconds, then AnalogDown about 1 second. r6 had 420/420 structurally valid and bracket-stable rows, 63 post-seed entries and 63 removals, all removals free-listed, peak 111 active, and final 98 active / 142 free. r10 had 420 rows, 416 accepted rows, 61 post-seed entries and 61 removals, all removals free-listed, peak 111, and final 98/142. Both observed Mario run action `0x04000440` and particle flag bit 0 in some rows. The counts vary with timing; repeatability is the same input recipe and demonstrated membership lifecycle, not identical event totals.

**Ground-pound and landing.** `issue52-groundpound-r9` and `issue52-groundpound-r14` used wake A500ms, then A+AnalogUp250ms, followed after 100ms by Z+AnalogUp150ms. r9's wake input at `00:10:45Z` preceded the action sequence at `00:10:56Z` by about 10 seconds; r14's wake at `00:17:22Z` preceded the sequence at `00:17:23Z` by about one second. r9 had 420 rows (416 accepted), 28 post-seed entries and 28 free-listed removals, peak 126 active, and final 98/142. r14 reproduced 28 free-listed removals and peak 126, returning to 98 active / 142 free; its sampler trace SHA-256 is recorded in the scalar manifest. The captured Mario action path included jump `0x03000880`, ground-pound `0x008008A9`, landing `0x0080023C`, and stop `0x0C00023E`. Ground-pound-associated post-seed entries observed in both runs used `0x800EB95C` (20) and `0x800EBBF8` (8), list 12. This supports repeatable lifecycle during the recipe and target-code corroboration of mask/spawn mechanisms; it does not prove a one-to-one causal mapping from each action to each spawned record.

### Measurement limits

RPM is read-only and each row is bracketed, but the emulator can update between reads. The contiguous snapshot and structural validation reduce cross-read inconsistency; they do not make a row atomic. Events between polls can be missed, and a slot can be freed and reused between polls without a generation counter. Therefore counts describe accepted observations, not a complete event log. The independent behavior-first-word read is labeled separately in raw private rows and is used only as supporting class evidence. Raw traces, input logs, ROM, save files, and screenshots remain local/private and are not part of this documentation.

The Ghidra project is a read-only static-analysis snapshot. Runtime script/code correspondence was separately checked by reading the current Project64 process, normalizing word-swapped RDRAM, hashing exact windows, and requiring a unique full-window match in the specified ROM. Thus a low-RAM address or bytes seen in an older snapshot are not presumed stable runtime evidence; the six current script windows and code/table windows are the ones listed above and in the manifest.

## Reproduction and sampler rules

Load the canonical courtyard state in Project64 with F7, confirm the courtyard and Mario's seeded position/action, then start the read-only sampler before guarded controller input. For run/reverse, wake with A, hold AnalogUp about 1.5 seconds, then AnalogDown about 1 second. For the ground-pound scenario, wake with A500ms, hold A+AnalogUp250ms, wait about 100ms, then Z+AnalogUp150ms. The observed r9 repeat waited about 10 seconds after wake before the sequence; r14 waited about one second. Both completed the same jump→ground-pound→landing→stop action path and free-list lifecycle, so the idle/wake interval is a precondition, not a measured action-duration requirement. Use the guarded #47 helper, whose PID/window checks and `finally` key release are required; the sampler must be the hidden concurrent process and read-only RPM only.

The sampler accepts a row only when pointer ranges stay within its single snapshot buffer, the before/read/after loop counter is stable, active/free chains are structurally valid with no overlap/unaccounted records, and membership totals reconcile to 240 pool slots. It compares each accepted snapshot with the previous accepted snapshot; invalid rows do not advance transition state. Each accepted entry is followed through later snapshots until the same slot is observed on the free chain, but the sampler has no object generation counter and cannot see free/reuse entirely between polls. The public scalar manifest gives the ROM, executable, seed, sampler, and input-helper hashes; trial-specific raw traces and input logs are private.

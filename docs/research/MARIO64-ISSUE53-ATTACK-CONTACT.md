# Mario 64 attack contact and target outcomes (#53)

**Status: complete for the bounded #53 scope.** This investigation maps the shared attack classifier, collision candidate selection, common overlap gates, five requested action families, selected target handlers, and one controlled accepted and one controlled rejected contact. The target is the USA rev0 ROM, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`. This is not an enemy AI catalog; that remains #54.

## Shared collision and contact path

The collision producer `0x802C8FE4..0x802C91EB` (ROM offset `0x83FE4`, 520-byte envelope, SHA-256 `6354C9C8548EBB8025FFD266F02DD8780F20BB4BD073438A8862B84C840ADAA4`) tests horizontal cylinder distance against the sum of radii at object `+0x1F8`, then vertical overlap using down-offset `+0x208` and height `+0x1FC`. It rejects non-overlap and either object's collision count `+0x76` at capacity four; on overlap it appends reciprocal object pointers to `+0x78`, ORs the counterpart's interaction selector `+0x130` into interaction mask `+0x70`, and increments both counts. A separate secondary hurtbox path (`0x802C91EC..0x802C9387`, offset `0x841EC`, 412 bytes, SHA-256 `6084070F166ECE3A887B0254917AC61A08BDF663734D7A1840FD4F6E25B20B51`) uses radius `+0x200` and height `+0x204`; its Mario-specific subtype-bit handling is not a general immunity flag.

The caller `0x802C93F8..0x802C94AB` (offset `0x843F8`, 180 bytes, SHA-256 `196F47B0B917E191C8304EF396A34FF7DDD3FAE2D9421DC2B210A11B340E093A`) requires both objects' `+0x9C` timers to be zero before overlap processing. The common list scan `0x802C9630..0x802C9723` (offset `0x84630`, 244 bytes, SHA-256 `C3057B9B66A2491D6DEF7FE4C5884FD277816966664128F856B0BB87F8DEA9F6`) includes distance `<2000` and active-flag `+0x74` bit `0x200` gates. The dispatcher `0x802503F0..0x802505C7` (offset `0xB3F0`, 472 bytes, SHA-256 `4847C064A9AE28BC90155BB30A206C10F45EF5C222C8D3CC99BBC200FDEE8B49`) selects a candidate from Mario object's collision list, consumes the interaction bit, skips candidates whose status `+0x134` has bit `0x8000`, and invokes the selector's handler. Its invulnerability/contact global is distinct from attack classification: `DAT_8033B272` is set from Mario action bit `0x20000` or Mario timer `+0x26 != 0`.

The 31-entry selector/handler table at `0x8032D950` has exact ROM match at offset `0xE8950`, 248 bytes, SHA-256 `414BEDFD32B42D5D8B0773FE093552EDE52E8604D98EDB1044ED26D82166ED52`. Relevant selectors are `0x200→0x8024F5CC` (breakable target), `0x400000→0x8024F1E0`, `0x8000/0x80/0x100000→0x8024F354`, `0x100→0x8024F4AC`, `0x2→0x8024FD2C`, `0x20000→0x8024EE44`, and `0x80000→0x8024F6A4`. Selector values identify dispatch routes, not target immunity or outcome by themselves.

## Classifier, result mapper, and Mario response

`0x8024C1D8..0x8024C51B` (ROM offset `0x71D8`, 836-byte envelope, SHA-256 `1195FBDA2C6CF62D4D23C1A3FB650585F0A11252FC4DDFC015C27D5D2D6BB6F2`) uses Mario action bit `0x800000` for the action-specific attack branches. The aerial fallback is separate and does not require that bit. It returns a contact mask according to action, flags, angle, velocity, action state, speed, and relative height. Zero means no classifier result for that candidate; it is not target rejection.

The five action families are:

| Family | Classifier branch and mask | Common result type | Target gate and Mario response on selector `0x200` |
|---|---|---|---|
| Punch | Actions `0x800380`, `0x800457`, and `0x18008AC` share the flag checks. Mario `+4` bits `0x100000` and `0x200000` are tested with facing delta strictly inside `(-0x2AAB, 0x2AAB)`; bit `0x400000` uses the stricter interval `(-0x4001, 0x4001)`. If multiple tests match, the later assignment wins. Do not infer a one-to-one action/flag pairing. | `2→type 1`; `4/8→type 2` | Breakable handler accepts these masks. For masks `2/4/8`, common response may change `0x800380→0x800457`, set Mario flag `0x40000`, and apply effect/sound/impulse. Trial 09 observed mask 2, target status `0xC001`, and that action transition. |
| Kick | `0x18008AC` uses those same three flag and facing-angle tests; mask depends on qualifying flags and branch order, not action ID alone. | `2→1`, `4/8→2` | Breakable handler accepts these masks and routes through the common response. No separate kick runtime trial. |
| Normal stomp | Descending aerial fallback: action bit `0x800`, vertical velocity `<0`, target below Mario yields mask `0x40`. Normal jump action `0x03000880` is a demonstrated input. | `0x40→type 3` | Selector `0x200` handler explicitly rejects mask `0x40`; trial 08 observed a stable descending overlap with target status unchanged and no Mario attack response. |
| Dive | `0x880456` or `0x188088A` can produce mask `0x20` through the action-flag or speed branch (the latter requires `abs(forward speed)≥26`). | `0x20→type 5` | Selector `0x200` explicitly rejects mask `0x20`. `0x8024CB58` is a **grab eligibility** gate, not the generic attack gate: its dive path requires target `+0x190` bit 4 clear. Dive runtime untested. |
| Ground pound | Actions `0x8008A9/0x108008A4` while descending, or landing actions `0x80023C/0x18800238` while descending and state zero, return mask `1`. | `1→type 4` | Selector `0x200` accepts mask `1`; common mapper and Mario response follow. Runtime untested. |

Slide-kick actions `0x18008AA/0x80045A` are supporting context only: mask `0x10→type 5`. The classifier's aerial fallback can also return `0x80→type 6` when rising below a candidate. These are not added as extra requested families.

`0x8024C51C..0x8024C617` (offset `0x751C`, 252 bytes, SHA-256 `528908FEA6A093C0D277DD2315FF4F00CF69A61CC8CC26DE8273094188B1217B`) maps masks `1→4`, `2→1`, `4/8→2`, `0x10/0x20→5`, `0x40→3`, and `0x80→6`, writing `target+0x134 = 0xC000 + type`. `0x8024D72C..0x8024D803` (offset `0x872C`, 216 bytes, SHA-256 `CBE0876299202CE27AA5F09C0E543D3653A8A86B1F1E96E645564902A8B12CDA`) implements selected Mario reactions; classifier or animation evidence alone does not establish target acceptance.

The breakable handler `0x8024F5CC..0x8024F6A3` (offset `0xA5CC`, 216-byte envelope including Ghidra gaps; canonical-ROM SHA-256 `0E68DA5FC1765AEF00EC25CE3C72846926CCF2DC3A878850B1DA5B52763495F9`) calls the classifier and explicitly returns without target-result mapping or Mario attack response when `(mask & 0x8F)==0`. Thus masks `0x10`, `0x20`, and `0x40` are explicit handler rejections for this target route; this is not proof of universal immunity. Other handlers differ: for example, `0x8024F4AC` accepts only mask bit `2` on its result path, while `0x8024EE44` has a separate zero-mask body-contact path that can write target status `0x8000`. Do not confuse that body-contact status with an attack result.

The live selector-`0x200` behavior script window was matched uniquely to canonical ROM bytes. Its 128-byte script at ROM offset `0x21B2E0` has SHA-256 `8A0C5B50152C4D9F20E5324E821834CF6CADC25BAB2C892E83A2E5FAEA7185DA`; opcode `0x0C` at script offset `+0x20` calls `0x802B1B2C`. That 132-byte function (ROM offset `0x6CB2C`, SHA-256 `2F66CAF2A7DDAAB498FC501E8D966464A9E1A394FDA951867A92F5E65D74569A`) calls `0x802A51AC`. The 124-byte function there (offset `0x601AC`, SHA-256 `DE2BDC7C75931DD3CF0051C2B582DF7058C4310CF74E916E176F729530F35BCE`) recognizes status whose high bits satisfy `(status & 0xC000)==0xC000`, clears the result field, and reports a consumed result. On that path, `0x802B1B2C` calls `0x802A4440` with argument 46; this 180-byte function (offset `0x5F440`, SHA-256 `EC0FB703C6E052381EDD39606973647C6DF1BE2518FE4061D3BA04B12903A574`) calls the generic effect path and object removal routine `0x802A0568`, which clears active flag `+0x74`. This exact script/consumer chain corroborates trial 09's `0xC001` result followed by deactivation. It does not identify the effect asset or establish other breakable variants' behavior.

`0x8024CBFC..0x8024CC7B` (offset `0x7BFC`, 128 bytes, SHA-256 `AB361E294EABA25B00514B0DED86BB6A22703528AB9EFA571FA9B0B51FC695D3`) searches the Mario **object** (`MarioState+0x88`) collision count `+0x76` and pointer list `+0x78`, matching candidate selector `+0x130`. `0x8024CB58` (offset `0x7B58`, 164 bytes, SHA-256 `22940FEC21179EAB13BAE8FF1295807F3843047017F3AAD63F29D313D1251911`) handles grab eligibility: the dive IDs require target `+0x190` bit 4 clear; punch IDs pass only when Mario action argument is below 2. These gates are separate from the breakable handler's mask filter. `0x8024FD2C` (offset `0xAD2C`, 320 bytes, SHA-256 `76F186E4E44D0B3DE486D65B210534937939817AC7060B6F54ED20B4223FABBD`) has distinct special `+0x190` and mask `0x0C` paths; it is not a generic attack gate.

Additional mapped consumers show why the target selector matters: `0x8024F1E0` (offset `0xA1E0`, 372 bytes, SHA-256 `D771DD4E62EF86C0D7AC25D0F014BD7B2067683E803026EDA92AFCA4FCB2B5C2`) handles selector `0x400000`, invoking the common result mapper and Mario response for nonzero masks; `0x8024F354` (offset `0xA354`, 344 bytes, SHA-256 `90F0C94A1DBFB19D4240A720563A9ECB97A7E36E5FEEE36DB3EF16DE4B1D7B7F`) handles selectors `0x8000/0x80/0x100000` with a mask-`0x40` special response; `0x8024F4AC` (offset `0xA4AC`, 176 bytes, SHA-256 `31E8BEE02F210267D5E7BFECEA6564AAB6545971359893187A348BDB996C2D84`) writes result type 1 and calls Mario response only on mask bit 2, otherwise takes its alternate handler; `0x8024EE44` (offset `0x9E44`, 436 bytes, SHA-256 `5F377F1F029CF7A5ED8F28719ACC39531C5ABD13CD6C87634E72827A3195C383`) has a distinct zero-mask body-contact/status path and accepts attack masks intersecting `0x7F` for the common mapper/response; and `0x8024F6A4` (offset `0xA6A4`, 260 bytes, SHA-256 `E652B173AF0F7892ECAD7B3258D99D8BA38691576DFE8164055089E7E4FC0D04`) routes mask `0x40` or specific Mario states into its result and Mario-action path, otherwise into a separate handler. Runtime outcomes for those selectors are untested.

## Controlled runtime outcomes

Both trials used ordinary gameplay input through the foreground-checked #47 helper and read-only process sampling. The candidate was a live selector-`0x200` breakable box, behavior base `0x800EC660`, initially status zero and active. The trial-08/09 traces are private and are not included in the repository. A scalar-only, de-identified extract is in [MARIO64-ISSUE53-ATTACK-CONTACT-TRACE-SAMPLES.jsonl](MARIO64-ISSUE53-ATTACK-CONTACT-TRACE-SAMPLES.jsonl).

In trial 09, B was held for 120 ms and released. Mario progressed from `0x800380` to `0x800457`; at the accepted-contact sample his forward speed was `−40`, the candidate result changed from zero to `0xC001`, and it remained in Mario's collision list. Mario health was 2176 and invulnerability timer zero. The next stable sample showed the candidate inactive and absent from that list; the following sample showed slot reuse, so no later fields are attributed to the candidate. This pairs a target result/lifecycle change with Mario's punch response and supports an accepted contact. It does not report target health or infer an unobserved damage value.

In trial 08, A initiated normal jump `0x03000880`. Five stable descending samples while overlapping the same candidate had Y values 179, 177.5, 172, 149, and 110 and vertical velocities −1.5, −5.5, −9.5, −17.5, and −25.5. The candidate stayed status zero and active, and Mario health/invulnerability stayed 2176/zero; no attack response was observed. The classifier's mask `0x40` and F5CC's explicit `(mask & 0x8F)==0` return establish this as a rejected contact on this handler route, rather than a classifier miss. Later landing action `0x0800034B` is not counted as an attack response.

Sampling is externally polled and not atomic; each row brackets a contiguous snapshot with a main-loop counter read before and after. Only equal-counter rows with validated Mario/object pointers, bounds, and active/free-list consistency are used; candidate identity is not followed after deactivation or slot reuse. Relevant reads include Mario action (`MarioState+0x0C`, U32), health (`+0xAE`, U16), invulnerability timer (`+0x26`, U16), Mario object's collision count/list (`MarioObject+0x76/+0x78`), and candidate selector/status/active flags (`+0x130`/`+0x134`/`+0x74`); position, velocity, and collision outcome are recorded as scalar values. The sampler recorded a 16-bit diagnostic at object `+0x154`, although that timer field is 32-bit. That diagnostic is excluded from all claims and the public scalar manifest. Dynamic fields reported above use their validated widths. The reviewed input helper SHA-256 is `2E78A7B6685C010C8FD2DDAD9D92815A77E9FB87202EAE6DA640A8579B0F9463`; the sampler SHA-256 is `D0730FA09678430B0BAF5DC0AFE541F898FFE509455F2E2EC8B8F66B9E257A4F`. Project64 portable executable SHA-256 is `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`; the private courtyard baseline fixture SHA-256 is `6E2C8265A8A9A19761BCC6CE29FA20694FAD5444B325B1F22CA987776A2D6DFE`. Runtime began from that baseline and reached BOB through normal castle entrance/painting gameplay, without memory writes or cheats. No raw RAM, process identifiers, emulator states, saves, ROM data, screenshots, or derived assets are published.

## Evidence and limits

The mapped PC-to-ROM relation is `ROM[0x1000,0xE8560) → PC[0x80246000,0x8032D560)`, with ROM offset `PC - 0x80245000` only inside that interval. Envelopes above include gaps in the listed length/hash. Functions outside the mapped span require separate exact-window evidence; the dispatch table was matched independently as stated above. Static function hashes are over canonical big-endian ROM bytes in the exact function envelope. The private focused exports, raw traces, and sampler remain under ignored `tools/issue11-local` paths.

Object pool/header lifecycle and shared field definitions are in [#52](MARIO64-ISSUE52-OBJECT-RUNTIME.md). Action recipes are in [#40](MARIO64-ISSUE40-CROUCH-SLIDE-DIVE-GROUND-POUND.md), and Mario health fields in [#44](MARIO64-ISSUE44-HEALTH-AND-HAZARDS.md).

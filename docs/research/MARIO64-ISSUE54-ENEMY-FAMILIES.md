# Mario 64 enemy families, contact, defeat, and projectiles (#54)

**Status:** reviewed bounded research complete. Parent #14 remains open. It inventories a finite, explicitly bounded set of enemy behavior-script candidates and follows four selected families into native code. It is not a complete Mario 64 bestiary. Target ROM: USA rev0, SHA-256 `17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91`.

## Inventory method and scope

The inventory starts with the pinned USA source `behavior_data.c` behavior-script arrays in [`n64decomp/sm64` at `9921382a68bb0c865e5e45eb594d9c64db59b1af`](https://github.com/n64decomp/sm64/tree/9921382a68bb0c865e5e45eb594d9c64db59b1af). The local parser enumerated 534 arrays, selected 22 explicitly named enemy candidates below, and scanned aligned four-byte command words in the target ROM's behavior-data region for candidate script signatures. This is a discovery procedure: the broad scan returned 16 unique opcode-pattern candidates and six ambiguous matches for the selected set. Neither a signature nor a source-array name proves behavior semantics. The four family groups with native behavior handlers corroborated here are Goomba, Fly Guy, Unagi, and waterbomb emitters/payloads. They span five of the 22 selected source arrays (`bhvGoomba`, `bhvFlyGuy`, `bhvUnagi`, `bhvWaterBomb`, and `bhvWaterBombCannon`); the other 17 selected arrays are inventory-only. Two supporting scripts outside the original 22-candidate scan—the overhead spawner and cannon-barrel bubble spawner—are recorded separately in the code manifest.

## Shared contact and object lifecycle

The object-pool layout, behavior-script dispatch, active/free lists, and sampling limits are documented in [#52](MARIO64-ISSUE52-OBJECT-RUNTIME.md). The common selector and action-family matrix are in [#53](MARIO64-ISSUE53-ATTACK-CONTACT.md); this report reuses those results rather than repeating the five-action matrix for each enemy. ## Ground walker: Goomba

The live Goomba behavior base `0x800EF8AC` uniquely matches the canonical ROM window at `0x21E52C` (128 bytes; SHA-256 `CFA9B2138406F696E1428BB34A337D36EAD9B83EDDB82C150C013041AECCA2DC`). Its native initialization is `0x802FF408` and update is `0x802FF96C`. Update action 0 runs the walk/chase state (`0x802FF600`); action 1 handles the Goomba having attacked Mario, with a separate huge-Goomba weak-hit case (`0x802FF868`); action 2 is its jump state (`0x802FF8E8`). In the walk state it chases inside 500 units, steering toward Mario with target speed selected from distance; farther away it uses a wander timer. The body handler checks the shared interaction path (`0x802FB518`) and its target-specific handler table. A normal-sized Goomba can move from action 0 to attacked action 1 and then jump action 2 on body contact; the body collision therefore may hurt Mario without defeating the Goomba. This differs from selected attack-result rows that set squish action `0x66`.

The Goomba hitbox template at `0x803328C0` has interaction type `0x8000`, unscaled radius 72 and height 50, damage 1, zero enemy-health field, and loot parameter 1. The runtime setter scales those dimensions; the observed ordinary Goomba graph scale is 1.5, so its live radius and height are 108 and 75. The common Goomba handler table at `0x803328F4` maps the normal-size contact result 3 to squish. Its attack result handler sets object action `0x66`; the standard squish state `0x802FB778` waits past timer 15 before the defeat handler `0x802FB128` clears active state when health is zero. Result 2 instead produces a knockback action. Large/weak variants have distinct table outcomes, so the ordinary-size result must not be generalized to every Goomba scale.

### Runtime representatives

Trial 02 recorded a stable body-contact sequence against a live Goomba: Mario’s object collision list contained the Goomba as its action changed from 0 to 1 and then 2; Mario health decreased from 1408 to 1344 to 1280 and later 1152 while the sampled invulnerability-timer field read zero. These sequential health reads are queued hurt processing across loop samples, not separate independent attacks. The target survived in jump action 2. This demonstrates body damage and enemy survival, not an attack by Mario.

Trial 12 used a normal jump and descending movement against another live Goomba. At stable sequence 106 (loop 49629), Mario was in jump action `0x03000880`, Y 193.56, vertical velocity −37.90; the target remained action 0 and collision was false. At sequence 107 (loop 49630), the target was action `0x66`, Mario’s object collision list contained the Goomba, and Mario was already at Y 255.51 with upward velocity +26, consistent with a bounce that began between samples. The first stable inactive target sample was sequence 124, loop 49647, after action `0x66` timer 17; it remained inactive for the rest of the trace. The transient status value `0xC003` was not sampled. Runtime action/bounce/removal evidence is paired with the native result-table and squish/removal path; the exact contact instant and status write are inferred between samples, not directly observed. Mario health stayed 2176 throughout.

The Goomba trial used ordinary foreground-checked controller input and read-only process sampling from the private canonical courtyard fixture, then reached Bob-omb Battlefield by normal gameplay. The input helper SHA-256 is `2E78A7B6685C010C8FD2DDAD9D92815A77E9FB87202EAE6DA640A8579B0F9463`; Project64 executable SHA-256 is `C257C662D4E0B2CE1732B7F4A7D5DD4682F604CB082BBDBFCE5181470D6DBFB8`; fixture SHA-256 is `6E2C8265A8A9A19761BCC6CE29FA20694FAD5444B325B1F22CA987776A2D6DFE`. Raw traces, save/state files, process identifiers, ROM bytes, and screenshots are not published.

Waterbomb variants are not interchangeable. The selected overhead payload has a contact/removal path; the cannon-barrel variant spawns a waterbomb through `0x80309CEC`, but that cannon payload is intangible to Mario in the examined variant. The BOB cannon object encountered at runtime had parameter `+0x144 = 1`, which prevents the native firing branch from dispatching a shot. A bounded capture observed no projectile: 660 rows total, of which 657 had stable loop-counter brackets, across two observation windows. This supports only “none observed under this disabled-parameter scene and bounded window,” not a general claim that the cannon never fires. The overhead-spawner path is a separate variant and is not ruled out by the disabled cannon.

## Runtime projectile trace and evidence quality

The east BOB overhead emitter (`0x800EFD0C`, radius 950) created payloads under ordinary gameplay input. In trial 14, payload generation 2 appeared at stable row 17 (loop 104177) in action 2, linked to the emitter. It descended from Y 2359.6 with vertical velocity −76, then reached Y 835.2 at row 21 (loop 104198) with movement flag `0x2`, the ground-contact flag. The same slot and generation left the active pool at row 22 (loop 104203) and was recorded free. A second payload followed the same sequence: spawn at row 29, ground contact at row 35 (Y 822.3, movement flag `0x2`), and active/free exit at row 36. Polling and read duration varied, and no intermediate action-3 state was sampled; the native action-3 cleanup path is established statically. No Mario hit is claimed: the payload interaction-status field remained zero in the sampled rows, and Mario health also changed during this trial without a sampled projectile-contact signal.

Earlier trial 11 independently observed an overhead payload birth, parent link, descent, and ground flag, but ended before a valid removal observation. The bounded cannon capture remains a separate variant: its runtime parameter `+0x144 = 1` prevents firing. It recorded 660 rows, 657 with stable loop-counter brackets, across two observation windows and no cannon payload entry. This supports only “none observed under this disabled-parameter scene and bounded window.” The cannon variant’s payload is intangible to Mario in the examined path.

The [sanitized trace index](MARIO64-ISSUE54-TRACE-SAMPLES.json) gives raw-file hashes and exact stable row/counter references for the Goomba and projectile representatives, plus a compact reproduction record. Raw JSONL traces, process identifiers, memory snapshots, screenshots, ROM bytes, and save/state files remain private. Every cited runtime row has an equal main-loop counter bracket. The rich object-pool captures also validate active/free-list structure; the earlier target-focused Goomba captures validate their selected Mario/target reads and counter brackets but do not claim whole-pool structural validation. The sample interval is non-atomic, so unsampled transitions are described as bounded between adjacent rows. Actor identity uses slot plus generation and behavior identity, and no post-reuse fields are attributed to the previous actor.

The projectile route used the foreground-checked Project64 helper and normal controller input. The 102-unit plateau fence was cleared with an ordinary jump; a later route pulse wandered away from the emitter; the health changes in that trial have no established cause. The successful trace came from a separate ordinary A-plus-direction press that moved Mario inside the emitter radius; no forced state or guest-memory write was used.

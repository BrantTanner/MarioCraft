# Mario 64 dynamic objects, moving platforms, and rider carry (#55)

**Disposition:** reviewed bounded research complete; parent #14 remains open. The target has a verified dynamic-geometry path, object-owned floor surfaces, platform attachment/displacement logic, and one controlled BOB checkerboard boarding followed by stable no-input carry and a later stable unowned airborne sample. That sample sequence does not isolate the precise detachment instant or cause. One low-ground retry failed to board and is recorded as a limit, not a second successful ride.

No guest memory was edited and no cheats were used; the canonical seed archive was preserved. Input trials used the foreground-checked, bounded Project64 helper; runtime sampling used `OpenProcess(QUERY_INFORMATION|VM_READ)` and `ReadProcessMemory` only.

The pinned source-navigation reference is [`n64decomp/sm64` commit `9921382a68bb0c865e5e45eb594d9c64db59b1af`](https://github.com/n64decomp/sm64/tree/9921382a68bb0c865e5e45eb594d9c64db59b1af). The selected BOB group is placed by the pinned level script at `(1612, 300, 4611)` with `bhvCheckerboardElevatorGroup` and parameters 0 and 40. A stable runtime sample observed its two live child boards at `(1612,470,4756)` and `(1612,530,4466)`; they were in opposite vertical phases, so the two Y=300 child positions are not simultaneous. The 44-byte target subplatform-script window at ROM `0x21B988` hashes to `44677DFCB1F67559FB7B71A939887826034BA2D6E8D6B7CE452E17BBFA154F91`. Its decoded command sequence declares opcode `0x00` with list ID 9, loads collision data, calls per-child initialization, sets home, then begins a loop that calls the checkerboard handler and ends the loop. This command declares the object's update list; it does not spawn a child. The separate source group initializer spawns the two subplatform children. The target child init copies the parent parameter into child state. The loop alternates vertical travel at `+10`/`−10` and signed pitch angular velocity at `+512`/`−512`; face pitch advances by the absolute angular-velocity value. It then refreshes dynamic collision. The live children shared the checkerboard behavior base and followed this parameterized motion; this is the one inventory candidate corroborated as a live target type.

Two other selected candidates have target-static native corroboration but no runtime actor match. The HMC elevator pattern at ROM `0x21AB30` maps to init `0x802ADDF8` (372 bytes, ROM `[0x68DF8,0x68F6C)`, SHA-256 `5B916F4FD88FAF0628EE3923E08E2D077489A62FAA8D7407599D1052632BD0EB`) and loop `0x802ADF6C` (44 bytes, `[0x68F6C,0x68F98)`, SHA-256 `DA4D60154A7AD06935389DE8B6A74D5947FD223403AFB2B4EB770766A51FEA3A`). The init indexes a height table from a behavior parameter and stores lower, upper, midpoint, and mode values; the loop dispatches through an action table. The swing pattern at ROM `0x21F2B8` maps to init `0x8031326C` (32 bytes, `[0xCE26C,0xCE28C)`, SHA-256 `E8E09D63E79218D38493C86B4862C9CA04B4762F6774492EC254DEB1CE92AB36`) and loop `0x80313294` (192 bytes, `[0xCE294,0xCE354)`, SHA-256 `66746F78E2E7F7F772701986BBA3A74BFE9FFAC1A46362CCF13A7EB2405B60DC`). The init sets a floating-point roll accumulator to 8192. The update adjusts a velocity accumulator by +4 when current face roll is negative and by -4 otherwise, advances the roll accumulator, assigns integer face roll, and records the new-minus-old roll as angular velocity. The behavior script calls the shared dynamic-collision loader after this update. These findings support selected native behavior paths only, not live HMC or swing placements or every action branch.

The frame pipeline resets dynamic partitions, updates object lists 11 and 9, applies existing Mario-platform displacement, resolves Mario/object collisions, updates the remaining lists and removals, then refreshes Mario's platform attachment. The target loader rebuilds dynamic collision only when time-stop bit `0x40` is clear, Mario is closer than the object's collision distance, and active flag `0x08` (different room) is clear. It builds world-space collision geometry from the object's model data and current transform. The transform path applies scale/position/angles to vertices; each transformed coordinate is converted to signed 16-bit `TerrainData` before dynamic surfaces are constructed and their owning object recorded. The loader only constructs the object matrix when its throw-matrix field is null. The render-object path clears that field after processing, allowing it to be rebuilt for a later pass; do not interpret the loader as rebuilding unconditionally.

The target field references are object position `+0xA0/+0xA4/+0xA8`, XYZ velocity `+0xAC/+0xB0/+0xB4`, face angles `+0xD0/+0xD4/+0xD8`, angular velocities `+0x114/+0x118/+0x11C`, collision-data pointer `+0x218`, and the 16-float transform matrix at `+0x21C`. Angle fields are 32-bit slots whose lower 16 bits supply the angle. The render throw-matrix pointer is `+0x50`; graph scale is `+0x2C/+0x30/+0x34`. Dynamic surfaces store their owner at `+0x2C`; Mario-object rider pointer is `+0x214`, and the global rider reference is `0x80330E34`. These are distinct fields, not interchangeable pointers or matrices.

`find_floor` searches dynamic and static floor partitions and returns the higher eligible surface. Mario attachment is a separate follow-up: `update_mario_platform` finds the floor at Mario's object position and associates both the global platform and Mario-object platform with `floor->object` only when a floor exists, has an owner, and the absolute difference between Mario-object Y and floor height is strictly less than 4 units; otherwise it clears those references. The carry wrapper runs only when time-stop is inactive and both Mario and the global platform exist. Displacement adds the platform's X/Z velocity and applies the previous-to-current rotation about its origin, updating Mario position and yaw. It does not directly add platform Y velocity; vertical movement is reflected through the floor/ground-step path. A floor query can therefore return a different nearby platform while the rider reference is null or names another platform.

These target details are corroborated in the pinned source at [platform displacement](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/platform_displacement.c#L18-L177), [object update ordering](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/object_list_processor.c#L623-L671), [dynamic surface loading](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/engine/surface_load.c#L658-L788), [floor selection](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/engine/surface_collision.c#L513-L573), [checkerboard behavior](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/behaviors/checkerboard_platform.inc.c#L14-L113), and [BOB placement](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/levels/bob/script.c#L24-L24). The exact target bytes remain authoritative if source labels and target behavior differ.

## Controlled runtime trial and result

The primary ride trace is the bounded capture `issue55-v3-ride-r27` (46 observations, 21 stable counter brackets; private-trace SHA-256 `E1016878D25F7F1E0F2B1FD22E1FEDBE5A3686BA3427FD8B2515DF05059312E9`). Starting from the reachable east BOB route, the capture began with Mario grounded at `(1841,768,4660.94)` and no input. Shortly before takeoff, the stable phase sample showed Mario still grounded there while the target board was rising at +10 units per update, horizontal pitch 0, and position `(1612,447,4470.85)`. A bounded `A+AnalogLeft` input for 650 ms then cleared the low wall and landed Mario on a live checkerboard board. The selected landing row has floor height 726, floor type `0x28`, and all three attachment checks—queried floor owner, global rider, and Mario-object rider—agree on that board. After input release, accepted stable rows in the subsequent interval (clearest examples: sequences 30 and 36) show idle action `0x0C000230`, zero raw/processed stick and buttons, zero Mario XYZ velocity and forward speed, and the same board owner in all three attachment checks. Counter-mismatched rows, including 34 and 35, are excluded.

Across stable row 30→36 (300 ms host time; nine counter increments), Mario X remained 1712.5977; Mario Y rose 764.9337→802.6511 and Z 4517.7295→4550.9043. Floor height matched Mario Y in both rows. Over the same interval the attached board moved from `(1612,734.7476,4474.2730)` to `(1612,791.2427,4500.9930)` and pitch from 2048 to 6656 angle units. This is carried position change while input and Mario velocity are zero; it is not merely the board moving under a stationary Mario. Floor-normal Y changed from 0.980759 to 0.802233, consistent with the sampled board tilt. The transform matrix is floating point while dynamic vertices are truncated to signed 16-bit coordinates, so normal correspondence is approximate, not an exact match.

At stable row 41, action was airborne `0x0300088E`, the floor query returned the other board at height 213, and both rider references were null while Mario remained near Y=756. Rows 37–40 have mismatched counter brackets and are excluded. Thus the capture proves an owned no-input ride segment and a later detached/unowned airborne state, but does not sample the transition instant or establish whether the rider left due to platform edge, rotation, or another contact branch. A subsequent no-input capture found Mario on the lower static floor; its sampler did not include health, so no damage conclusion is made. The no-input control capture (`issue55-bob-platform-ride-r1`, 200 observations, 148 stable; private-trace SHA-256 `DCB244FEB90882329FE0BFF88DB622B402522FD81B0502D907FD86A4849DB7AB`) independently held Mario fixed at `(2549.3943,802.9091,5003.4214)` while the two boards' positions changed; all sampled controller input remained zero. This separates platform motion from Mario input before boarding.

A low-ground retry used `Z` for 250 ms followed by `A` for 750 ms, with both key releases recorded. It did not board. Backflip action `0x01000883` appeared in the three accepted stable rows 576–578 (loops 173901–173903): Mario Y was 27, 19, and 7, with vertical velocity −8, −12, and −16; all were already descending. Y=27 is the highest accepted sample, not a proven peak. Stable row 579 (loop 173904) was the landing action at floor height 0. The last stable pre-backflip row 574 (loop 173899) showed the board at Y=252.25 and ceiling-height candidate 213; the candidate was 199 in the first stable descending row. An overhead collision with the board or nearby geometry is plausible, but the capture does not uniquely identify the surface. This is a failed boarding attempt, not evidence that backflips cannot board the platform. Health was 384 in all accepted rows. Capture `issue55-v4-backflip-r44` had 1485 observations, 1170 stable brackets, SHA-256 `DE151EBBF9A2A0A517789DF7998D4E527F4B1C62B27A003C316944F127C090D8`; its unneeded raw data remains private.

## Limits and handoff

The inventory is deliberately bounded. Only the BOB checkerboard group is tied through script pattern, target native calls, and live child transforms to observed platform motion. HMC elevator and swing candidates have target-static init/update corroboration but no live actor match; remaining selected patterns are structural candidates. The source/target mapping is exact for the listed ROM windows. An attempted RPM read of the high native-code window, using the base validated for low-RAM reads, failed; no live-RPM code hash is claimed and no cause is inferred. The low-RAM runtime values and transform matrices were read-only and tied to the exact process and ROM identity above.

The trial does not map every platform type, all surface mesh winding/quantization cases, multiple simultaneous riders, ride timing under pause/time-stop, indirect object collisions, or exact detachment causes. It does not claim that a queried floor surface is always Mario's attached platform. #12 remains the collision/query/surface reference, #52 owns object-list and behavior dispatch lifecycle, and #54 owns enemy/projectile interaction. Hand #15 the BOB placements, course catalog, and progression/script coverage; keep those course-specific inventories out of this issue. Remaining tasks are broader platform-family verification and a targeted controlled departure cause if a later issue needs it.

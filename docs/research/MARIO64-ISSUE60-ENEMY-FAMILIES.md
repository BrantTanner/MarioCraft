# Mario 64 enemy-family coverage (#60)

**Status:** static inventory plus a selected Bob-omb runtime sequence; #60 stays open pending separate projectile contact with Mario. Target ROM is USA rev0, SHA-256 17CE077343C6133F8C9F2D6D6D9A4AB62C8CD2AA57C40AEA1F490B4C8BB21D91.

## Method and evidence classes

The bounded rows are the 17 source behavior arrays listed in #60 and previously inventory-only in #54. Source navigation is pinned to [n64decomp/sm64 at commit 9921382a68bb0c865e5e45eb594d9c64db59b1af](https://github.com/n64decomp/sm64/tree/9921382a68bb0c865e5e45eb594d9c64db59b1af). For each row, the source behavior-array size and target-ROM candidate windows were compared. Candidate windows were decoded for native-call or behavior-jump operands, then those native targets were read in the canonical ROM Ghidra project. A matching opcode shape alone remains structural evidence; unique native operands and list/parameter values raise confidence but do not prove a complete source rebuild identity.

Native code was inspected with Ghidra 12.1.4 against the already imported canonical ROM using read-only, no-analysis mode. Where the project had no function boundary at several candidate entries, temporary function boundaries were created for inspection only; project changes were discarded. Numeric function envelopes and SHA-256 references are in the companion code manifest. The previously established PC-to-ROM mapping applies only to the half-open PC range [80246000, 8032D560) (ROM offset = PC minus 80245000). Thwomp's collision-model helper 803839CC is outside that mapping; its exact 416-byte code-window correspondence to ROM 10074C is separately cross-referenced from #55, without extending the global mapping.

The public #54 evidence remains in force: Goomba was the live enemy-body-contact representative; Fly Guy and Unagi were native-static only; the overhead waterbomb trace established spawn, descent, ground contact, and pool removal but not a hit on Mario. The #53 five-action matrix, #56 pickup work, #55 platform carry, and #15 course/progression work stay with their existing tickets.

## Runtime coverage and limits

In a normal BOB entry, followed by an immediate pause, two guarded samples at `2026-10-27 02:42:23.936` and `02:42:24.828 UTC` found active slot 67 at `(-1900, 0, 3450)`, action 0 and behavior pointer `0x800EE2F4`; Mario was at `(-6525.123, 0, 6431.123)` with health 2176 and one life. A separate guarded double read of the 56-byte behavior window at `0x800EE2F4` uniquely matched the candidate at ROM `0x21CF74`, SHA-256 `E7B0739A517A782E94AEECDC56F9D0EEC0B2FD92D4E415E3B25FA5E97DDFBC08`. The main-loop counter advanced during the separate full-ROM search. These are non-atomic paused observations of presence and candidate identity, not a witnessed AI transition, Mario contact, enemy outcome, or uninterrupted object lifetime. The [safe scalar record](mario64-issue60-bobomb-passive-scalars.json) gives the measured bounds.

A subsequent guarded BOB run selected a live instance of that behavior. At main-loop counter 2810267 it was in action 0 with fuse unlit; at 2810314 it was in action 2 with fuse lit and timer 1. At 2810317 Mario's collision list contained that instance; Mario's health was 1920, and the selected body had interaction selector 2 and damage value 0. A single B input produced Mario's moving-punch action while the held-object pointer stayed null; this did not establish a successful grab or attack.

After monitored movement, the selected instance progressed from fuse 137/action 2/active flags 257 to fuse 152/action 3, and then fuse 158/action 3/active flags 0, with the same behavior pointer. At the next stable sample Mario's interaction pointer and collision list identified a child whose parent was the selected instance, selector 8, and damage value 2. Health had changed 1920 to 1856 and the hurt counter was 7; the game was paused. This is one observed self-detonation and first damage tick, not a measured full damage drain. A separate guarded double-read of the child's resident behavior at `0x800EE690` uniquely matched ROM `0x21D310` over 128 bytes, SHA-256 `D65708FFD6204C525982BDDD35DFEC0872A9A27D9D59EA94A089A8B945926516`. The ROM search spanned multiple main-loop counts; it was a separate resident-code observation rather than an atomic child-lifetime proof. The 72-byte behavior array at the same ROM offset hashes to `0F1C885E77178C12D16738B6C966928C8ACA248A29B9D1B0942A36BAF17E843C`; its native init at `0x802EAA8C` (68 bytes) and loop at `0x802EAAD0` (288 bytes) are bounded and hashed in the scalar record. The static behavior encodes selector 8, damage value 2, radius 150, height 150 and down-offset 150. Native loop logic removes the explosion after its timer reaches 9; that later child removal was not observed in this paused sample. The [runtime scalars](mario64-issue60-bobomb-runtime-scalars.json) record sample boundaries and limitations. Other named families remain untested for their own runtime outcomes.

Projectile contact with Mario remains a separate gap. The #54 overhead-waterbomb trial observed projectile spawn, descent, ground contact, and active-pool removal; it did not sample Mario contact. The cannon payload is a separate variant and its observed BOB instance had firing disabled by its parameter. For Snufit, the static producer-to-payload path is now mapped, but there is no controlled scene with a spawned ball contacting Mario and a paired interaction/health observation. Thus neither the Snufit projectile-hit outcome nor a Mario response is established. #60 does not meet its controlled-runtime acceptance criteria and stays open; a later runtime pass must distinguish Mario contact from spawn, flight, ground/wall contact, and removal.

The static pass does not repeat #53’s five-action matrix, #56 pickup work, #55 platform carry, or #15 course placement/progression. It makes no bestiary-completeness claim.

## Reproduction and provenance

For a conditional replay, enter BOB normally, pause, locate an active Bob-omb by its live behavior and home position near (-1900, 0, 3450), and verify the scene, health, other actors, and current object identity. Resume briefly under continuous guarded sampling and approach its home area and facing direction until the source-described chase gate is met; pause on unexpected damage or a changed actor identity. Record action, fuse, Mario collision pointers and health, then observe the lit fuse in short guarded movement intervals with safe ground and other actors checked. Capture its action, flags, child parent and interaction fields at detonation. Locations and actor movement can vary; this documents a conditional procedure, not a second observed replay or an atomic trace. The guarded input helper and process/ROM checks are the same as the [#56 runtime procedure](MARIO64-ISSUE56-INTERACTION-EVIDENCE-PARTIAL.md); no guest writes or saved-state loads were used. Pinned [Bob-omb source](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/behaviors/bobomb.inc.c) provides the named state and fuse semantics.

ROM identity is recorded above. The behavior-array inventory and candidate-window hashes are in the private research inputs used to produce the sanitized values here. Native envelopes were exported from the pre-existing Ghidra project with the private helper Issue60CandidateNativeExport.java; use the canonical ROM project and the command shape documented by #54’s native exports, with read-only/no-analysis mode. The resulting private decompilation log and helper remain outside publication. No ROM/RAM bytes, source dumps, private captures, save states, screenshots, or host paths are included in this draft.

Evidence boundary: #54’s Goomba runtime samples and overhead-waterbomb lifecycle samples remain valid carry-forward evidence, but neither fills any of the 17 new rows or proves projectile contact with Mario. Parent #14 remains open pending #60 and its other remaining dependencies.

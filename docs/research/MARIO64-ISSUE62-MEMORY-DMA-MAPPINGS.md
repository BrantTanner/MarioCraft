## Transfer, decode and addressing

`dma_read` rounds the source interval length up to 16, invalidates the destination data cache, submits normal-priority PI reads in chunks no larger than `0x1000`, and blocks for each completion message before advancing. The aligned transfer can extend beyond the nominal source end. `dynamic_dma_read` allocates before copying; `load_segment` installs its base only on successful allocation. This is source behavior; no individual PI transfer timing was observed. [memory.c](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/memory.c#L254-L296); queue setup is in [#61](MARIO64-ISSUE61-BOOT-INPUT-SCHEDULING.md).

For compressed load, source reserves aligned compressed input at the right, DMAs it, reads decoded length at header offset 4, allocates output at the left, decodes, installs the output base, then frees temporary input on success. Texture loading instead decodes to the fixed `gDecompressionHeap` and installs that base. The US [decoder](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/asm/decompress.s) uses header offsets 8 and 12 for back-reference and literal streams, 32-bit control words beginning at offset 16, and writes until the declared output end. A one bit selects a literal; a zero selects a two-byte token with length high nibble + 3 and backwards distance low 12 bits + 1. This code path does not itself establish bounds validation for malformed streams.

`set_segment_base_addr` stores a physical base masked by `0x1FFFFFFF`. `segmented_to_virtual` selects by the high byte, adds the low 24 bits, and sets `0x80000000`; `virtual_to_segmented` subtracts the selected base. The graphics setup emits the first 16 table entries as RSP segment commands. This is address translation, not rewriting payload pointers or relocating machine instructions. Source declares 32 entries; no bounds check is shown in these helpers. [memory.c](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/memory.c#L53-L104).

One raw and one compressed path are explicit at game startup: `setup_game_memory` loads entry segment `0x10` raw and segment `2` compressed. The level interpreter's `LOAD_RAW` and `LOAD_MIO0` invoke the same respective helpers; `EXECUTE` pushes pool state, loads a raw script bank and resolves its entry; `EXIT_AND_EXECUTE` pops then pushes before replacing it; `EXIT` pops and restores continuation. `INIT_LEVEL` pushes after clearing objects and areas; `CLEAR_LEVEL` clears and pops. These are source paths, not observed transitions. [game setup](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/game/game_init.c#L624-L638), [level interpreter](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/src/engine/level_script.c#L91-L119).

The linker declares Goddard/menu code at fixed pool address `0x8016F000` (`0x801C1000 - 0x52000`); the [intro](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/levels/intro/script.c#L23) and [menu](https://github.com/n64decomp/sm64/blob/9921382a68bb0c865e5e45eb594d9c64db59b1af/levels/menu/script.c#L23) scripts request its fixed-address load. These are overlay-like replacements of memory regions with separately linked code or data, not evidence of a general runtime linker. The examined engine and fixed loaders copy prelinked bytes and perform cache maintenance; no relocation-record walk or instruction fixup occurs in these functions. This is a bounded conclusion about these paths, not proof that no other code anywhere can relocate anything. Segment rebasing resolves segmented data addresses separately.

## Two observed loaded-state moments

Two previously recorded read-only Project64 samples, at `2026-10-26T05:24:53.8970715Z` and `2026-10-26T06:06:30.8750296Z`, identify the same emulator process/start and executable, the same ROM hash and matching live ROM prefix, and level 9/course 1 (BOB). No new input or capture was made. Selected segment `0x09`, associated with source texture command `0x1A` and encoded ROM interval `[0x32D070,0x334B30)`, had table base `0x801C1000` in both samples. Its 47,104-byte decoded candidate and both complete compared blocks have SHA-256 `93D2F56838A24B534BBC5C0ACEB3FC496304408A77F77DCFD7E731CC59C0B744`. Equal before/after state counters were respectively 385015 and 459756, and the target base remained stable during each read. These counters are bracketing indicators, not frame numbers or proof of atomic snapshots. Fourteen compared blocks matched candidates in both samples; segment 7 had the same one-byte difference documented in #58. Identity and matching at two moments do not prove uninterrupted retention, a load, a replacement, or an unload between them. The segment 1 base differed between samples, but absent payload identity it cannot establish a transition.

The sanitized [native manifest](MARIO64-ISSUE62-NATIVE-MANIFEST.json) records these selected windows and the BSS operands.

## Acceptance and remaining unknowns

The documented source, range and lifetime table, selected native correspondences, #58 reconciliation and two identified mapping observations satisfy the bounded #62 criteria. The comparison shows the same mapping and content at two moments; it does not claim a load/unload transition or uninterrupted retention. The issue permits existing snapshots and only permits a transition claim when one was recorded.

Observed initial transfer completion, the full pre-entry PIF/IPL3 sequence, native correspondence outside the selected windows, and any intervening mapping changes remain unknown. Runtime access remains deferred; do not infer success or failure of an earlier input attempt from an unchanged log. Parent #16 remains open for its other work and original criteria. No gameplay implementation or prototype is authorized before the #17 and #18 gates.

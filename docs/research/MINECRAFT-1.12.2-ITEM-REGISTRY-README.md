# Reproducible original-byte probe

From the workspace parent directory, run:

```powershell
& (Join-Path (Resolve-Path 'MarioCraft') 'docs/research/reproduce_minecraft1122_registry.ps1')
```

From inside the `MarioCraft` directory, run `& '.\docs\research\reproduce_minecraft1122_registry.ps1'`. The script resolves the repository root and local tools, verifies the original server jar SHA-256 and the three extracted class hashes, extracts and decompiles only `ain.class`, `aow.class` and `aox.class` into the ignored `tools/inspection/issue32/reproduction/` directory, parses the registration-call grammar, compiles/runs the Java reflection probe, and asserts source/runtime identity and lookup counts. Outputs remain under ignored local `tools/inspection/issue32/reproduction/`; the published CSVs are the captured results.

The exact 25 runtime-library paths needed by the server bootstrap are listed relative to the MarioCraft root in `MINECRAFT-1.12.2-REGISTRY-LIBRARIES.txt`. The runner expects the existing local dependencies and tools; it does not download or alter game bytes. CFR 0.152 and JDK 8 are resolved as `..\tools\cfr-0.152.jar` and `..\tools\java\temurin8\jdk8u504-b01` relative to the repository. The official server and client jar SHA-256 values are recorded in the main dossier; the client recipe and loot resource-entry hashes are in `MINECRAFT-1.12.2-ITEM-RESOURCE-HASHES.csv`.

`Minecraft1122RegistryProbe.java` reflectively initializes the official Minecraft 1.12.2 server bootstrap and writes item IDs, block IDs, and `Item.getItemFromBlock` lookup rows. It does not launch a world or write to either game jar. The captured result is `MINECRAFT-1.12.2-REGISTRY-RUNTIME.csv`; item registration metadata parsed from the original Item class is in `MINECRAFT-1.12.2-ITEM-REGISTRY.csv`. Original server class hashes for registration, stack variants and mutation routes are in `MINECRAFT-1.12.2-ITEM-PATH-CLASS-HASHES.csv`.

The probe uses original obfuscated class and method identities from the unmodified server jar. MCP/SRG mapping files label classes and methods for navigation; they do not establish behavior. The relevant original class hashes are `ain.class` (Item), `aow.class` (Block), `aox.class` (Blocks), `ni.class` (Bootstrap), and `fh.class` (RegistryNamespaced), all present in the hash CSV.

## Verified results

The runtime output has 411 registered items, 254 registered blocks, and 254 block-to-item lookups. Direct row counts yield 53 lookups returning `minecraft:air` (one legitimate air-block row plus 52 non-air blocks without a block item) and 201 non-air lookup results. The registration-call parser accounts for 209 direct numeric-ID registrations, 56 custom block-item registrations and 146 default block-item registrations: 411 insertions total, including 202 block-item registrations (one is air). There are three additional textual `ain.a(` occurrences inside helper implementations (forwarding overloads), not additional insertions. Runtime/source comparison found 411/411 identical `(numeric ID, registry key)` item pairs, 254/254 block ID/key pairs, and 202/202 block-item registration relations including air, with zero differences. The runtime lookup partition is 1 air block + 52 non-air blocks returning air + 201 non-air blocks returning registered items = 254.

## Variant and identity coverage

A registry key alone does not identify every stack state. For item stacks, the stable base identity is item registry key plus metadata/damage; stack count affects quantity, while NBT can change behavior or display. `ItemStack` serialization carries item identity, count, damage and optional tag. The finite item registry is fully cataloged in the CSV; metadata and NBT are represented as variant families rather than falsely expanded into one row per possible stack.

Metadata-bearing block-item families include stone/dirt/planks/saplings/sand; logs and leaves; sponge, sandstone, tall grass and flowers; wool, carpet, stained glass, panes and terracotta; slabs, double plants, monster eggs and stone bricks; prismarine; and anvil damage. Item families include coal/charcoal, fish, dyes, golden apples, skulls, banners/shields and spawn eggs. Damage is also used as durability state for tools, weapons and armor. The affected original classes and exact class hashes are in the path-hash CSV; the original recipes and loot-table entries, each individually hashed, are in the resource-hash CSV. Resource counts are cross-checks, not evidence that every stack state is distinct.

NBT-driven behavior includes spawn-egg `EntityTag`; potion `Potion`, `CustomPotionEffects` and color; map identity; `BlockEntityTag` contents for banners, shulkers, spawners and other block entities; `SkullOwner`; firework/explosion data; written-book author/title/pages/generation/resolution; enchantments and stored enchantments; repair cost; unbreakable state; attribute modifiers; CanDestroy/CanPlaceOn; and display name/lore/color/hide flags. Exact payload values and nesting are data-dependent; arbitrary combinations are not a finite catalog. Forge `ForgeCaps` is a separate stack capability payload. Arbitrary mod-defined registry entries, tags, recipes or capabilities are outside the official vanilla-plus-Forge target and cannot be enumerated without naming a mod set.

## Mutation and join coverage

The vanilla server join points are `NetHandlerPlayServer.processClickWindow`, `processCreativeInventoryAction`, `processHeldItemChange`, `processPlayerDigging`, `processEnchantItem`, `processTryUseItem`, `processTryUseItemOnBlock` and `processUseEntity`; `PlayerInteractionManager` validates block breaking/harvesting and right-click actions; `Container.slotClick` applies the click-mode branches; `EntityPlayerMP` owns the player inventory/container transitions; `EntityItem.onCollideWithPlayer` and `EntityXPOrb.onCollideWithPlayer` are the collection joins. Item behavior is reached through `Item.onItemUseFirst`, `onItemRightClick`, `onItemUse`, `onItemUseFinish` and `itemInteractionForEntity` callbacks and the corresponding overrides in specialized item classes. `CommandGive`, `CommandClearInventory`, `CommandReplaceItem`, `CommandEnchant` and `CommandXP` are direct command sinks; `/execute` and `/function` delegate to command sinks, while `AdvancementRewards` grants recipe unlocks, loot-table rewards and XP. Those classes, packet classes and core containers are individually SHA-256 listed in the path-hash CSV. Class names and method labels use MCP navigation names; the hash rows preserve exact original obfuscated class names.

All player container mutations are covered: `PICKUP`, `QUICK_MOVE`, `SWAP`, `CLONE`, `THROW`, `QUICK_CRAFT` and `PICKUP_ALL`, including cursor-stack changes, close-window return and transaction confirmation. Item callback routes include first-use, right-use, block-use, entity interaction, food/potion consumption, tool durability, armor/equipment and death. The direct inventory commands are `/give`, `/clear`, `/replaceitem` and `/enchant`; `/xp` changes player experience. `/execute` and `/function` can invoke those command sinks, so enforcement belongs at the common player mutation path. Advancement reward execution can grant recipe unlocks, loot-table rewards and XP; it is a second reward path and belongs behind the player-only progression gate.

World joins include crafting outputs/remainders, furnace recipes and ticking, brewing recipes/effects, villager trades, shipped loot-table resources and code-defined drops. Representative exact data joins include vanilla JSON recipe matches (432 individually hashed entries), the 82 individually hashed loot tables, `FurnaceRecipes`/`TileEntityFurnace`, `PotionHelper`/`TileEntityBrewingStand`, `EntityVillager`/`MerchantRecipe`, and item callback methods. The exact client jar paths, uncompressed sizes and SHA-256 for every recipe and loot-table JSON are in the resource-hash CSV, so item identifiers can be cross-checked against the hashed resource set. Vanilla container/workstation routes include player crafting, workbench, furnace, brewing stand, enchanting, anvil, merchant, beacon, chest, dispenser, hopper, horse and shulker inventories. EntityLiving mob pickup/equipment and mob loot/death are traced separately so player restrictions do not suppress ordinary mob behavior.

Forge adds capability-backed inventory access through `IItemHandler` and item-handler wrappers/slots, entity and tile attachment/access hooks, and player lifecycle/save clone hooks. These are mapped Forge `.2859` navigation evidence, clearly separated from the vanilla original-byte proof; no claim covers arbitrary third-party mods. The implementation seam is player-specific server validation and player pickup/XP collision handling. Keep mobs, structures, effects, item entities, mob equipment and world-generated loot operational. Player mining/placement, inventory, hunger, armor and item use are excluded from the agreed MVP; this research records their 1.12.2 routes rather than implying an implementation change.

The connected-client inventory UI and player save/reload were observed in the vanilla client for #33. Issue #34 later enabled an isolated Forge 14.23.5.2864 title/world-save run through a generated-artifact repair, but did not test mod-specific inventory behavior. This ticket establishes static registry and mutation-route coverage and does not claim Forge runtime UI/save evidence.
